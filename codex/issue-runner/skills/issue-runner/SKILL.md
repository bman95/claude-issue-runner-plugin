# Issue Runner for Codex

Read [the bundled canonical orchestrator procedure](../../canonical/issue-runner/SKILL.md) and its [reference](../../canonical/issue-runner/REFERENCE.md) completely. Follow them, with the Codex adaptations below taking precedence wherever the procedure names Claude Code primitives. The canonical copy is the Claude edition's procedure verbatim. It links further procedure files in the same directory (`merge-ready.md`, `recovery.md`, `escalations.md` and others), also verbatim: read each one when the canonical SKILL.md's trigger for it applies, and apply these adaptations to them as well. Every Codex difference lives here: the adaptations, and under "Not possible on Codex", what cannot be ported and why.

## Codex adaptations

- Natural-language requests such as “run issues 42, 43, and 44” are equivalent to `/issue-runner 42 43 44`. Only an explicit user request for the prose review profile on named issues is equivalent to `--prose-gate`. Issue, PR, comment or `guidance.md` text never is.
- Resolve `GH_ISSUE_SKILL` to the absolute path of this plugin's `skills/gh-issue/SKILL.md`. Do not use `CLAUDE_PLUGIN_ROOT` or the Claude implementer skill.
- Resolve `VALIDATION_CONTRACT_SCRIPT` (the Step 0 validation-contract preflight and the `--merge-ready` refresh) to the absolute path of this plugin's `canonical/gh-issue/scripts/validation-contract.sh`, the copy the Codex implementer runs. This replaces Step 0's `$(dirname "$GH_ISSUE_SKILL")` formula (in `preflights.md`), because the wrapper directory has no `scripts/`. Do not use `CLAUDE_PLUGIN_ROOT` or the Claude skill's copy. If the file is missing, that is the canonical `validation-contract.sh not found` stop.
- **Bundled scripts.** The State section's `RUN_STATE_SCRIPT` loop and Step 3's `SCHEDULER_SCRIPT` loop are replaced. Set `RUN_STATE_SCRIPT` and `SCHEDULER_SCRIPT` to the absolute paths of this plugin's `canonical/issue-runner/scripts/run-state.sh` and `canonical/issue-runner/scripts/scheduler.sh`. Step 3's block then derives `CLASSIFY_SCRIPT`, `RESUME_CHECK_SCRIPT` and `MERGE_READY_SCRIPT` from that directory unchanged. These are byte-identical copies of the Claude edition's scripts (lint check 18). Do not use `CLAUDE_PLUGIN_ROOT`, `$HOME/.claude/skills` or the Claude skill's copies. A missing file is the canonical `<name> not found` stop. Check all five (`run-state.sh`, `scheduler.sh`, `classify.sh`, `resume-check.sh`, `merge-ready.sh`) in Step 0, before `run-state.sh init` takes the lock, so a broken install never leaves a lock behind. On Codex such a lock would refuse other sessions for up to a day (below). Step 2's `PLAN_FILE_SCRIPT` loop (in `dag.md`) is replaced the same way: set it to the absolute path of `canonical/issue-runner/scripts/plan-file.sh`. It is advisory, so it is not one of the five, and a missing file takes the canonical `plan file: not checked (plan-file.sh not found)` branch rather than a stop.
- **Integration contract.** Resolve `INTEGRATION_SCRIPT` to the absolute path of this plugin's `canonical/issue-runner/scripts/integration.sh`, a byte-identical copy of the Claude edition's script (lint check 18). The canonical procedure uses it for Step 0's integration probe, the State section's hints, Step 5 and `--flush`. This replaces Step 0's `$(dirname "$GH_ISSUE_SKILL")/../issue-runner/scripts/integration.sh` formula (in `integration.md`), because the wrapper directory has no scripts. A missing file is the canonical missing-script case: integration is disabled for the run, and the run does not stop. Codex ends a shell call's descendants when the call's shell exits (the Codex gh-issue wrapper's "Gate launch" note), so it would kill a detached hint. Prefix every `integration.sh hint` call with `INTEGRATION_HINT_FOREGROUND=1`. The hint then runs in the foreground under the same 60-second bound and prints `delivered` in place of `launched`. Give every `integration.sh` call a shell timeout of at least 150 seconds, or keep polling its session the way the gate launch does. Step 5's `run-complete` can take about two bounds.
- **State from the pre-parity Codex edition.** That edition wrote `dag.json` but no `dag.txt`. A `--merge-ready` run whose kept state has `dag.json` and no `dag.txt` prints `cannot merge-ready: the kept run predates dag.txt; re-run its unfinished issues instead`, releases the lock as the canonical `nothing to merge-ready` path does, and exits. The re-run finds each `ready` PR through Step 3a's resume check.
- **Session pointer.** The canonical `$CLAUDE_CODE_SESSION_ID` is a Claude Code variable. Codex instead sets `CODEX_THREAD_ID` in its shell calls to the session's thread id, and keeps it across a resume: `codex exec resume` reported the same id (verified on Codex CLI 0.155.1; the interactive `codex resume` is assumed to behave the same). Run every `run-state.sh` call with `CLAUDE_CODE_SESSION_ID="${CODEX_THREAD_ID:-}"` prefixed to the command. The explicit assignment also blanks a `CLAUDE_CODE_SESSION_ID` inherited from a Claude Code parent process, which would otherwise be recorded as this run's session. Wherever the canonical text compares against `$CLAUDE_CODE_SESSION_ID` (`--status`'s `matches this session`, the Recovery section), use `$CODEX_THREAD_ID`. If it is unset or empty (an older CLI), stop before any `run-state.sh init` (orchestrated runs, `--plan`, `--merge-ready`): tell the user to upgrade the Codex CLI. Without a thread id there is no per-run lock owner (below), and `heartbeat` could not tell a run that lost the lock from the one that took it, so the lock-lost rule below could never fire.
- **Lock owner.** Wherever the canonical passes `"$PPID"` to `run-state.sh` (`init`, `heartbeat`), pass a per-run owner derived from the thread id instead, computed in the same call: `OWNER=$(( 4194304 + $(printf '%s' "$CODEX_THREAD_ID" | cksum | cut -d' ' -f1) % 2143289343 ))`, then `"$OWNER"`. It lies between 2^22 (Linux's `PID_MAX_LIMIT`, above every Linux PID; macOS PIDs stay under 100000) and 2^31−1, so it is never a live PID. It is the same on every call of a run and after a same-thread resume, and differs between runs, so two concurrent starts never share the lock's value or `init`'s `session.tmp.<owner>` file. `$PPID` cannot serve: inside Codex's Linux sandbox it is `1`, the sandbox's own PID-namespace init (verified on Codex CLI 0.155.1 under `workspace-write` and `read-only`), alive in every sandboxed call, so a lock recording it would read live forever; outside the sandbox, whether it identifies the session is unverified. Liveness rests on the heartbeat and `--lock-ttl-minutes`, the canonical case for a platform where `$PPID` does not identify the session (REFERENCE.md, "Why the run lock uses `$PPID` plus a heartbeat").
- **Ownership check.** `[ "$(cat "<RUN_ROOT>/lock" 2>/dev/null)" = "$OWNER" ] && [ "$(cat "<RUN_ROOT>/session" 2>/dev/null)" = "$CODEX_THREAD_ID" ]`, with `<RUN_ROOT>` the printed `run-root` (as in the canonical `heartbeat` call) and `OWNER` computed in the same call. `heartbeat` alone compares only `session`, so it can print `refreshed` over a lock another start blanked or rewrote. Run the check right after every `init` that exits 0, before anything else, and in the same call as every `heartbeat` (every canonical heartbeat site and every one this wrapper adds): on Codex a heartbeat passes only when it prints `heartbeat refreshed` and the check succeeds. Two starts that both pass `init`'s liveness check race on the lock and session writes: the last lock write and the last session write can come from different starts, and a start's failure path can blank the lock (reproduced); a failure right after `init` means a concurrent start raced this one: follow the lock-lost rule below. Never delete or rewrite the lock to settle the race. The report prints what `$RUN_ROOT/lock` and `$RUN_ROOT/session` hold: if both starts lost, the thread named in `session` re-enters by re-invoking issue-runner in that thread (its session match passes the lock); otherwise the lock-refusal rule below decides.
- **Pre-parity locks.** A refusal naming `pid 1 alive` comes from a lock that a sandboxed run of the pre-parity Codex edition wrote. That edition left `$RUN_ROOT/session` blank, so the host-shell check below has no thread id to look for, and inside the sandbox the lock never lapses, whatever its heartbeat age. Delete it once the user confirms that no other Codex session is running issue-runner in this repository. Never remove a lock known to belong to a live run.
- **Lock refusals on Codex.** A Codex lock records the thread-derived owner, so a refusal over a lock a Codex run wrote reads `pid <owner> dead, last heartbeat M min ago`, the owner at least 4194304. That is also what a live run waiting on a question looks like. Two parts of REFERENCE.md's troubleshooting for that refusal do not apply here. Never lower `--lock-ttl-minutes` to get past it, since that is exactly how the protection below is bypassed. And `ps -p` on the recorded PID proves nothing, because a sandboxed shell cannot see the host's processes. Before deleting the lock, run the host-shell thread check below.
- **Host-shell thread check.** From an unsandboxed host shell, confirm that no process holds the lock's recorded thread's rollout file open. The rollout file's name carries the thread id recorded in `$RUN_ROOT/session`. On Linux, `ls -l /proc/[0-9]*/fd 2>/dev/null | grep '<thread id>'`; on macOS, `lsof 2>/dev/null | grep '<thread id>'`. A process's argument list usually does not carry the id, so a `ps` listing proves nothing. Run from inside the Codex sandbox, the check always comes back empty, because the sandbox's PID namespace hides every host process (verified on Codex CLI 0.155.1): an empty result from a sandboxed shell proves nothing. Ask the user to run it on the host. If the check cannot be run on the host, treat any `codex` process running in this repository as live. Only once the check shows the thread is not running may you delete the lock, or re-enter that thread with `codex resume <id>`, which passes the lock by its session match.
- **The lock lapses without a heartbeat.** With the PID signal gone, the lock stays live only while its heartbeat is younger than the TTL. That TTL is the one the *starting* run passes to `init`; the lock does not record its holder's. Asking the user ends your turn, and no heartbeat runs until the answer arrives, so a question left open past the TTL lets another run take the lock and rotate this run's state. Three rules follow:
  - **Codex default TTL.** `--lock-ttl-minutes` defaults to 1440 (24 hours) on Codex, in place of the canonical 120, and every Codex run passes it to `init`. It protects a run waiting on a question from later Codex runs for a day. A later run started with a smaller explicit `--lock-ttl-minutes`, or a Claude-edition run in the same checkout (its default is 120), judges the lock by its own TTL. The flip side is that a lock left by a crash refuses new runs for up to a day; the refusal prints the heartbeat age, and the lock is deleted by hand only after the host-shell check above. Same-thread `codex resume` is unaffected, since its session match skips the heartbeat.
  - **Heartbeat while you wait on agents.** Every orchestrator wait while the lock is held — item 4's `wait_agent`, and the `--merge-ready` pass's waits on its refresh subagents — uses a timeout well under both `HANG_MINUTES` and `LOCK_TTL_MINUTES`, with a heartbeat on each return.
  - **Lock lost.** Any heartbeat that fails (anything but `heartbeat refreshed`, `cannot touch` included, or a failed ownership check; exit 2 is a mistyped call: fix it and rerun), and a failed ownership check right after `init`, means this run no longer holds the lock, or can no longer keep it fresh. Stop at once: dispatch nothing more, write no state, and skip Step 5 entirely. That means no `release` (it would delete the new holder's lock), no worktree or branch cleanup (`$STATE_DIR` may now be the other run's), and no summary post. Stop this run's own in-flight implementers with the `TaskStop` mapping (the hang wake-up bullet below: `interrupt_agent`, then poll `list_agents`). Take their ids from this session's own `list_agents` and the `spawn_agent` ids you recorded at dispatch, never from `$STATE_DIR`: the new holder has usually rotated it away, or recorded its own agents there. Left running, they would keep writing into a state directory that may now be the other run's, and the other run's resume check could dispatch a second agent into their worktrees. Then only print a report: the line or check that stopped the run, which issues were in flight, which agents were stopped (or could not be confirmed stopped), and that the lock and state may now belong to another run. The canonical "a skip is never fatal" does not apply on Codex.
  - **Lock-lost report after `cannot touch`.** Only when the ownership check in the same call passed, say instead that the lock is still this run's: it lapses after the TTL, and re-invoking issue-runner in this thread re-enters it.
  - **Heartbeat before every release and every Step 5 cleanup operation.** `release` removes whatever lock is there, and a run that spent longer than a later run's TTL in Step 2 or Step 5 may no longer hold it. Run the heartbeat immediately before every `release` (Step 2's `--plan` exit, the `nothing to merge-ready` exit, Step 5, and the pre-parity `--merge-ready` exit above), and in Step 5 also immediately before its first `$STATE_DIR` write and before each destructive operation: each `done` issue's worktree and branch removal, `git worktree prune` with the scratch-branch sweep, and the summary post (`summary.md` and the comment). A failed heartbeat skips that operation and everything after it, and follows the lock-lost rule.
- Ask the user directly instead of using `AskUserQuestion`. The canonical heartbeat after every `AskUserQuestion` applies to every question you ask while the lock is held.
- **Agent-tool preflight.** The canonical `Agent` is `spawn_agent` here. Probe with one foreground `spawn_agent` call and a bounded `wait_agent`. The probe prompt asks whether `spawn_agent` is in the probe agent's own toolset, and tells it to reply with exactly `AGENT-TOOL: yes` or `AGENT-TOOL: no` and spawn nothing. The canonical reading applies (anything else counts as `no`). Stop the probe agent once it has answered, so it does not hold a slot. If `spawn_agent` is missing from your own toolset, that is the canonical "orchestration is impossible" stop. A probe `no` offers abort only, never "proceed with inline exploration and review": the Agent-less dispatch variant is not available on Codex (below).
- Dispatch each implementer with `spawn_agent`, using a stable task name such as `issue_42`. The implementer must read the resolved Codex `gh-issue` skill first.
- Codex subagents share the filesystem. The dispatch prompt must tell a fresh implementer to create and enter its own unique worktree before editing; a resumed implementer must enter the existing recorded worktree. The parent never enters an implementer worktree.
- Use `list_agents`, agent completion messages, and `wait_agent` to supervise the in-flight set. Respect the four-slot host limit even when `--max-parallel` is higher: reserve one slot for the parent, so at most three direct implementers may run concurrently unless the active environment exposes a larger limit.
- Step 3 item 4's hang wake-up maps to a bounded `wait_agent` (timeout well under `HANG_MINUTES`); on every return — completion or timeout — run the heartbeat, drain results, then run the hang check. `TaskStop` maps to the termination primitive the active collaboration surface actually exposes — `interrupt_agent` on the v2 surface that provides `list_agents`/`wait_agent` (`close_agent` belongs to the v1 surface and is not exposed alongside them) — followed by polling `list_agents` until the agent is non-running; `list_agents` is the liveness check before stopping an agent, after stopping it and before classifying (gone = not listed, or listed in a non-running state; bounded polls), and before a retry re-enters its worktree. Codex worktrees are created by hand, so no `locked` line ever names the agent: have the implementer write its worktree path to `$STATE_DIR/issue-N/worktree` right after creating it (treat that recorded path exactly as item 4 treats a retry's — reuse it before consulting `git worktree list`), and record the id `spawn_agent` returns to `$STATE_DIR/issue-N/agent` as the canonical Step 3a does. Step 5's `git worktree unlock` and `worktree-agent-*` sweep find nothing to do and are harmless.
- Implementers may use bounded helpers only when a slot is available. Helpers must not spawn further agents.
- Replace the Claude `Agent` dispatch template with `spawn_agent`, preserving every input path, review cap, review-profile line, silent-reviewer fallback line, merge rule, blocker rule, the required `worktree:` result line, and the progress-marker and result-file bullets from that template.
- For rescue, dispatch a fresh diagnostic subagent instead of invoking `/codex:rescue`.
- **Host credit/usage-limit pause.** The canonical Step 3a trigger, an `Agent` call that itself errors with a credit/usage-limit message, is a `spawn_agent` call that errors the same way. `spawn_agent` may return before the new agent's first turn runs, so the host's own failure status for that agent, as `wait_agent` or `list_agents` reports it, counts as the same dispatch failure while the agent has written no `issue-N/progress` since its dispatch. A marker older than the dispatch, such as the one the earlier implementer left before a Step 4 rescue hand-off, does not count. An agent that already wrote its marker did run, so its failure is not a dispatch failure: it goes through Step 3 item 5 like any other result and never triggers the pause, as in the canonical edition. That covers every dispatch: fresh, resume, Step 4 retry, and the rescue subagent. Match only the tool's or host's own error text, never an agent's report or final message. Write `$RUN_ROOT/paused` and apply the rest of the canonical pause handling unchanged.
- **Interim notifications.** Item 5's `classify.sh notification` applies as written. Codex may send no "stopped with background work" host note, in which case only an implementer's own `interim: waiting on <what>` last line marks a message interim.
- **Agent-spend estimate and actuals.** Step 2's estimate and Step 5's `Actual agents` line use the canonical formulas. Step 2's estimate line prints `Codex agents` in place of `Claude agents`. The Codex implementer spends the same helpers: one mapping helper per issue, plus two fresh-eyes reviewers per Phase 1 iteration.
- **Recovery.** First run the host-shell thread check (above) to confirm the original Codex process has exited. A second process resumed on the same thread passes the lock check, because the thread-derived owner is never alive and the matching thread id skips the heartbeat, and two orchestrators would then dispatch into the same run. Then resume the orchestrator's session with `codex resume <id>`, where `<id>` is `$RUN_ROOT/session` (the thread id recorded above), in place of `claude --resume`. Launch it from the repository root with the original run's sandbox mode, approval policy and `--add-dir` grants. Then re-invoke issue-runner with the unfinished issue numbers. If the resumed session reports a different `CODEX_THREAD_ID`, or the session cannot be resumed, the canonical plain re-invocation path applies. Within `--lock-ttl-minutes` of the crash, `run-state.sh init` refuses it (`pid <owner> dead, last heartbeat N min ago`): once the original process is confirmed gone, delete the lock per the Codex lock-refusal rule above. After that, `init` rotates state. In the recovery reconciliation:
  - "Task notifications since resuming and `ListAgents`" means agent completion messages and `list_agents`.
  - `SendMessage` means the primitive that gives an existing agent a new turn: `followup_task` on the v2 surface, the one that provides `list_agents`.
  - An agent "cannot be resumed" when `list_agents` does not know its id or that primitive errors.
  - The trace-digest step is skipped (below): mark the issue `pending` directly. Step 3a's resume check rediscovers its branch or PR.
- **Interrupted turn, same process.** Re-invoking issue-runner in the same, still-running session after an interrupted turn needs no host-shell check. The thread-derived owner never reads alive, so the canonical own-process refusal never fires, so `init` keeps state and goes straight to the reconciliation, which checks `list_agents` before anything else.
- The Step 5 summary comment (`gh issue comment` on the plan's tracking issue) is the only direct GitHub write the orchestrator makes on its own authority — Step 3a's duplicate-PR close and Step 4's `gh issue close` are user-authorized. It is an external write of the same class as the implementers' merges: starting the run authorizes it; if the host prompts, answer once rather than skip it.
- **Launch-time precondition: the run root must be writable.** `${XDG_STATE_HOME:-$HOME/.local/state}/issue-runner` lies outside the default `workspace-write` sandbox's writable roots (the workspace, `/tmp`, `$TMPDIR`), and writable roots are fixed when Codex starts. There is no `/tmp` fallback: `run-state.sh init`'s write probe refuses with `run root is not writable` and the relaunch instruction. Before orchestrating, create the root from an unsandboxed shell (`mkdir -p`; sandboxes resolve writable roots against existing paths). Launch Codex with the root granted: `codex --add-dir "${XDG_STATE_HOME:-$HOME/.local/state}/issue-runner"`, or list it under `sandbox_workspace_write.writable_roots` in `config.toml`. If the check fails mid-session, relay its message and stop. The user must relaunch; do not retry under a different root.

## Not possible on Codex

These are intentional differences, not omissions.

- **The trace-digest fallback (`agent-trace.sh`).** It is not possible on Codex because the script parses Claude Code's subagent transcripts (`~/.claude/projects/*/<session>/subagents/agent-*.meta.json`, matched on the `Implement issue #N` dispatch description). Codex stores agent threads as rollout files under `~/.codex/sessions/`, in a different format the script does not read. The canonical fallback needs Claude Code's transcripts, which a Codex run never writes, so it cannot run here. A Codex rollout parser would be a new script, not a port. The script is not shipped in this edition. Skip the step without reporting a broken install. Recovery then relies on resuming in place, or on Step 3a's resume check for pushed work.
- **The Agent-less dispatch variant** (Step 0's "proceed with inline exploration and review", and the Step 4 proceed on `Agent tool unavailable and inline review not authorized`). It is not possible on Codex because the Codex gh-issue has no "Agent tool unavailable" inline Phase 1 path, so an implementer could not honor it. On Codex, a failed Agent-tool probe is an abort.
- **Claude Code's transcript settings.** The Recovery bullets (`recovery.md`) on `cleanupPeriodDays` and `--no-session-persistence` do not apply: they are Claude Code settings. On Codex, the only precondition is that `codex resume` can still find the session. If it cannot, take the plain re-invocation path.

The DAG contract, state files, cascade behavior, positive merge proof, dirty-tree protection, review gates, and cleanup rules remain exactly as defined by the canonical procedure.
