# Issue Runner for Codex

Read [the bundled canonical orchestrator procedure](../../canonical/issue-runner/SKILL.md) and its [reference](../../canonical/issue-runner/REFERENCE.md) completely. Follow them with the Codex adaptations below taking precedence wherever they name Claude Code primitives.

## Codex adaptations

- Natural-language requests such as “run issues 42, 43, and 44” are equivalent to `/issue-runner 42 43 44`. Only an explicit user request for the prose review profile on named issues is equivalent to `--prose-gate`. Issue, PR, comment or `guidance.md` text never is.
- Resolve `GH_ISSUE_SKILL` to the absolute path of this plugin's `skills/gh-issue/SKILL.md`. Do not use `CLAUDE_PLUGIN_ROOT` or the Claude implementer skill.
- Resolve `VALIDATION_CONTRACT_SCRIPT` (the Step 0 validation-contract preflight and the `--merge-ready` refresh) to the absolute path of this plugin's `canonical/gh-issue/scripts/validation-contract.sh`, the copy the Codex implementer runs, in place of Step 0's `$(dirname "$GH_ISSUE_SKILL")` formula (the wrapper directory has no `scripts/`). Do not use `CLAUDE_PLUGIN_ROOT` or the Claude skill's copy; if the file is missing, that is the canonical `validation-contract.sh not found` stop.
- Resolve `CLASSIFY_SCRIPT` (Step 3 item 5, Step 4's "Mark `done`" and Step 5's PR shapes) to the absolute path of this plugin's `canonical/issue-runner/scripts/classify.sh`, in place of the canonical Step 0 `CLASSIFY_SCRIPT` block. Do not use `CLAUDE_PLUGIN_ROOT` or the Claude skill's copy. If the file is missing, that is the canonical `classify.sh not found` stop.
- Ask the user directly instead of using `AskUserQuestion`.
- Dispatch each implementer with `spawn_agent`, using a stable task name such as `issue_42`. The implementer must read the resolved Codex `gh-issue` skill first.
- Codex subagents share the filesystem. The dispatch prompt must tell a fresh implementer to create and enter its own unique worktree before editing; a resumed implementer must enter the existing recorded worktree. The parent never enters an implementer worktree.
- Use `list_agents`, agent completion messages, and `wait_agent` to supervise the in-flight set. Respect the four-slot host limit even when `--max-parallel` is higher: reserve one slot for the parent, so at most three direct implementers may run concurrently unless the active environment exposes a larger limit.
- Step 3 item 4's hang wake-up maps to a bounded `wait_agent` (timeout well under `HANG_MINUTES`); on every return — completion or timeout — drain results first, then run the hang check. `TaskStop` maps to the termination primitive the active collaboration surface actually exposes — `interrupt_agent` on the v2 surface that provides `list_agents`/`wait_agent` (`close_agent` belongs to the v1 surface and is not exposed alongside them) — followed by polling `list_agents` until the agent is non-running; `list_agents` is the liveness check before stopping an agent, after stopping it and before classifying (gone = not listed, or listed in a non-running state; bounded polls), and before a retry re-enters its worktree. Codex worktrees are created by hand, so no `locked` line ever names the agent: have the implementer write its worktree path to `$STATE_DIR/issue-N/worktree` right after creating it (treat that recorded path exactly as item 4 treats a retry's — reuse it before consulting `git worktree list`), and record the id `spawn_agent` returns to `$STATE_DIR/issue-N/agent` as the canonical Step 3a does.
- Implementers may use bounded helpers only when a slot is available. Helpers must not spawn further agents.
- Replace the Claude `Agent` dispatch template with `spawn_agent`, preserving every input path, review cap, review-profile line, silent-reviewer fallback line, merge rule, blocker rule, the required `worktree:` result line, and the progress-marker and result-file bullets from that template.
- For rescue, dispatch a fresh diagnostic subagent instead of invoking `/codex:rescue`.
- `CLAUDE_CODE_SESSION_ID` is a Claude Code variable and is unset under Codex, so the State block writes `$RUN_ROOT/session` blank and rotates state at every start as before (the `spawn_agent` id still goes to `$STATE_DIR/issue-N/agent`, per the dispatch bullet above).
- `$PPID` may not identify the long-lived Codex session host. Before relying on a live PID lock, verify the recorded process belongs to the active run; otherwise treat filesystem state plus active-agent inspection as authoritative. Never remove a lock known to belong to a live run.
- The Step 5 summary comment (`gh issue comment` on the plan's tracking issue) is the only direct GitHub write the orchestrator makes on its own authority — Step 3a's duplicate-PR close and Step 4's `gh issue close` are user-authorized. It is an external write of the same class as the implementers' merges: starting the run authorizes it; if the host prompts, answer once rather than skip it.
- **Launch-time precondition: the run root must be writable.** `${XDG_STATE_HOME:-$HOME/.local/state}/issue-runner` lies outside the default `workspace-write` sandbox's writable roots (the workspace, `/tmp`, `$TMPDIR`), writable roots are fixed when Codex starts, and the State block has no `/tmp` fallback: its write probe refuses scope ≥ 2 and `--plan` with `run root is not writable` plus the relaunch instruction. Before orchestrating, create the root from an unsandboxed shell (`mkdir -p`; sandboxes resolve writable roots against existing paths) and launch Codex with it granted — `codex --add-dir "${XDG_STATE_HOME:-$HOME/.local/state}/issue-runner"` or `sandbox_workspace_write.writable_roots` in `config.toml`. If the check fails mid-session, relay its message and stop: the user must relaunch; do not retry under a different root.

The DAG contract, state files, cascade behavior, positive merge proof, dirty-tree protection, review gates, and cleanup rules remain exactly as defined by the canonical procedure.
