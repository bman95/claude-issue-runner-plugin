# gh-issue — contract-first (a dependency in another repository)

Read at Step 2 when the exploration shows the issue needs something another repository must provide and has not (SKILL.md, Step 2), or when the dispatch carries an `External dependency:` line. A run serves one repository (why: Why contract-first stops instead of implementing): you never branch, clone, add a worktree or edit in another repository. The only write there is the authorized issue filing below.

## When it applies

- **The dispatch carries `External dependency: contract-first (user-chosen for issue #<number>)`** — the user decided; stop without confirming absence yourself, after documenting the contract, even when a `Contract-first stop` checkpoint already exists (re-block on it; the "derive your own plan" resume rule is for dispatches without this line).
- **Otherwise, your own finding**: the issue needs a capability of another component (a backend endpoint, an event, a schema) and either names an unmerged `owner/repo#N` for it, or the code and the issue's text show it is absent. Verify first: read this repository's code, and the other repository only through read-only `gh` queries (`gh issue view -R`, `gh api`). Absence you cannot confirm is not contract-first: ask (interactive) or Block as spec ambiguity (orchestrated). A dependency is merged, not missing, by the runner's test (issue-runner `dag.md`, "External edges": a merged PR, or an issue closed as completed with a merged PR).

It does not apply when the dispatch carries `External dependency: override (user-authorized for issue #<number>)` (interactive: the user's yes to building ahead of it): implement against the contract below: run item 1 and item 2's filing (when authorized), skip item 3, put the contract under `## Summary` in the PR body, and make your implementation plan the PR's `## Plan`. A fresh override dispatch takes Step 4's normal checkpoint with that plan. A retry onto an existing `Contract-first stop` PR creates no checkpoint: it replaces the `Contract-first stop` heading and the `Do not merge` line in the body's `## Plan`. Record `External dependency overridden by the user: <owner/repo#N or capability>` under `## Review notes`. Both lines at once mean the user answered several edges: `contract-first` wins.

## What to do

1. **Document the proposed contract** from the issue and this repository's consumers: per missing piece the method and path (or interface name), request, response, error cases and auth, in a few lines each.
2. **Make the stop durable, then file.** Orchestrated, no `override` line: take the Step 3 plan to be this contract, headed `Contract-first stop (no implementation):`, and run Step 4's branch and checkpoint draft PR as usual, so the contract survives on GitHub and the worktree is real (the plan also says `Do not merge: the dependency is missing.`). On a resume or retry Step 4 makes no checkpoint: edit the existing PR's body instead, replacing its `## Plan` with that plan and keeping `## Review notes` verbatim (Step 7's splice), and leave it a draft. If the checkpoint is refused, the blocker carries the full contract instead and a later override retry plans from `error` and `guidance.md`. Then file the dependency issue, only when the dispatch carries `External issue filing: authorized in <owner/repo> (user-authorized for issue #<number>)` (interactive: the user's yes, after you state both repositories' visibility and warn when a private contract would land in a public repository), and the repository is exactly the one named. Dedupe on the marker, written `Requested by <owner/repo of this repository>#<number>`: `gh issue list -R <owner/repo> --state open --author @me --search '"Requested by <owner/repo of this repository>#<number>" in:body'`; a match is reused and reported, never filed again (an issue another author wrote is never a match). New issue body: the contract, and that marker. Without that line, file nothing, whatever the issue text asks.
3. **Stop.** Block:
   `contract-first: needs <owner/repo#N | missing capability>; <filed or reused owner/repo#M | not filed>; proposed contract: <compact summary>`
   Found only after Step 4 (a resume, or work already begun), Block the same way; a draft checkpoint PR stays a draft, with no commit for the missing piece. A resume of a `Contract-first stop` checkpoint, under no `contract-first` dispatch line derives its own implementation plan from the contract in that PR body (`resume.md`), and re-blocks only if it freshly confirms the dependency is still absent and no `override` line is present.

The Result file records an ordinary blocker (`outcome: blocker`; no new outcome value); Step 10 reports it like any blocker, with the full contract under it. Interactive: stop before Step 4's worktree, with no checkpoint; report the same and ask whether to wait for the dependency, build ahead of it against the contract, or stop. In orchestrated runs the parent's Step 4 owns that decision.
