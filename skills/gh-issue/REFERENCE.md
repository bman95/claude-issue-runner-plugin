# gh-issue — Reference

The rationale behind the rules in [SKILL.md](SKILL.md) and the files it links one level deep (review-profile.md, review-loop.md, validation.md, resume.md, interactive.md, merge.md). SKILL.md points at an entry by its title: `(why: <entry>)`. Entries in the orchestrator's [REFERENCE.md](../issue-runner/REFERENCE.md) are cited as `issue-runner REFERENCE.md, <entry>`.

## Rationale notes

- **Why reviews never run through the Skill tool.** `/review`, `/security-review` and `/codex:review` are terminal-output producers: invoking them via Skill() hands them the rest of your turn, so the steps after the review never run. `/codex:review` is also `disable-model-invocation: true`. Reviews therefore run as fresh subagents or inline, and codex runs via Bash; the ban holds for every step of gh-issue.
- **Why inline-review authorization is settled at Step 2.** You have the full tool surface of a top-level Claude Code session — spawn subagents via `Agent` where the host grants it to subagents, run `codex`/`gh`/`git` via Bash, edit files, search — but some hosts hand subagents a toolset without `Agent`. Step 2 (exploration) and Step 8 Phase 1 (fresh-eyes review) each carry an inline fallback for that case. Phase 1's fallback is a recorded degradation that only the dispatch prompt (orchestrated) or the user (interactive) can authorize, because a review by the implementing context is a weaker merge authority (issue-runner REFERENCE.md, "Why a review pass by the implementing context is a weaker merge authority"). It is settled at Step 2, before implementing, so that an orchestrated run whose dispatch prompt does not authorize inline review returns the Phase 1 blocker right there rather than after opening a PR, and an interactive run asks there rather than after the work is done. Helpers work in the implementer's own worktree (they inherit its cwd, which is correct — hence never `isolation: worktree`), and depth stops with them: the implementer is the integrator, helpers return results and only it commits, pushes and merges (issue-runner REFERENCE.md, "Subagent depth").
- **Why the progress marker is a locator.** An in-flight issue is otherwise opaque to the orchestrator: its `status` file says `implementing` and nothing else. The one-line marker says where the implementer is; it is a locator, not a log, so it carries only the step id and the PR. It is best-effort and free: one local write, no API calls; `2>/dev/null` comes *before* the file redirect so even the redirect's own error is silenced, and `|| true` means a missing directory or unwritable path never fails a step. Interactive runs have no state path in play, so they write nothing. It never surfaces in the deliverable (PR body, `## Review notes`, commits) and lives outside the repository, so nothing is ever staged.
  It is informational only: the orchestrator reads it for `--status` and post-mortems and never treats it as evidence of merge or convergence — those come from GitHub (`gh pr view --json state`) and the review loop's own verdict — and a crashed implementer leaves the file at whatever step it last entered. The one thing the orchestrator acts on is the file's **mtime**: an implementer whose marker has not moved for longer than the runner's `--hang-minutes` threshold is stopped as hung, which is why it must keep moving during a long Step 5 (per commit) and while a reviewer or gate pass is outstanding (every wake, Step 8 "Liveness"). See also issue-runner REFERENCE.md, "Why the progress file is best-effort and never proof" and "Why the hang rule reads the file's mtime but not its content".
- **Why the result file is advisory.** The progress marker says where the implementer *is*; the orchestrator also needs to know how it *ended* without parsing the Step 10 prose, so `result.json` is written on every orchestrated exit — a blocker or failure returned from any step included, not only after a merge. Its key set is lint-checked against the orchestrator's copy (issue-runner's), so both SKILL files spell it identically. It is written once, immediately before the final message, one JSON object on one physical line: that is why `blocker` escapes `"`, `\` and every control character (`\n`, `\t`). The quoted `'EOF'` delimiter disables shell expansion, so the only escaping needed is JSON's own — inside any string value, `branch` and `worktree` as much as `blocker`. `blocker` carries the same text as the final message. Like the progress marker it is best-effort and free (one local write, no API calls, `|| true` so an unwritable path never fails the step) and never surfaces in the deliverable (not in the PR body, `## Review notes`, or a commit; it lives outside the repository).
  It is advisory for status and authoritative for telemetry: the orchestrator reads it before the prose but still verifies `merged` against GitHub (`gh pr list --head <branch> --state merged`) and never derives `done` from the file alone, while its review-loop telemetry (iterations, gate passes, degradations, waivers, checks) comes only from these files. The order — `step=10` marker, then this file, then the final message — keeps the final message (with its `worktree:` line and the Step 10 report) as the parent's fallback when the file is absent (a crash before the write). The Step 10 `validation:` line is prose only by design, so the key set does not grow for it.
  `outcome` maps to exit classes: `merged` needs Step 9's own `gh pr view --json state` = `MERGED`; `ready` is the `Merge mode: no-merge` dispatch's stop after the checks gate passed and the PR was marked ready; `blocker` covers everything the parent can route to a human or a retry; `failed` is an environmental failure the parent cannot resolve (an irresolvable merge conflict inside Step 9's base-freshness recipe is a `blocker`, not `failed`), and a refused Step 4 checkpoint push never fails the run. `checkpoint` `skipped` is a different fact from `refused`: the run chose not to take the Step 4 checkpoint, so nothing was refused; the parent's summary flags it because the crash-recovery guarantee did not hold. `review_profile` `revoked` means standard review applied from the revocation on; an exit before Step 8 reports the profile as authorized, and `phase1_iterations` 0 shows no review ran under it. See issue-runner REFERENCE.md, "Why `result.json` is advisory for status decisions and authoritative for telemetry".
- **Why the contract is read from the base tip.** "Run the tests" means something different in every project — lint, unit tests, builds, containers, E2E — so the project says what it means, and the plugin never names or assumes any of it; the script runs the declared command through `bash -c` from the worktree root and reads only its exit status (0 passes). The trusted copy is the freshly fetched tip of `origin/<base>`: base-branch content a human already merged, the same copy the runner's Step 0 probes, and the copy this PR is merged into (Step 9's base freshness merges that tip in before the merge). Nothing this PR writes to the file, and nothing an issue, PR body, comment or `guidance.md` says about validation, can change what validation the PR runs: that text is data (Step 1's trust rule), and a PR that rewrote the file could otherwise switch its own validation off. So a project's policy changes only by landing on the base branch — which is also the recovery for a broken contract: fix it there, re-run, and the next validation reads the fix. `changed` mode compares the file against the merge-base, so a sibling's change that landed on the base is never mistaken for this PR's.
  A PR that edits the file is a policy change a human authorizes: its edit is inert for this PR (the base copy already ran), and what needs a human is letting it become the next PR's policy — orchestrated, it is a blocker before the PR is marked ready whatever the merge mode, because `--merge-ready` merges a `ready` PR mechanically, so a policy change must never reach `ready` on the run's own authority. The contract pins *which command* runs; the command itself runs in this PR's checkout, so a PR that edits what it executes (the scripts it names, a linter's configuration) changes what validation *does* — an ordinary diff for the Step 8 reviewers, not a policy change the contract-change check catches. Step 9 still runs the script with `full` when Step 3 saw none declared because the script re-reads the base tip each time, so a `full` line that landed after Step 3's probe is never missed. See also issue-runner REFERENCE.md, "Why validation is declared by the project and read from the base branch, never guessed by the implementer or taken from the PR".
- **Why the script never comes from the worktree.** The first candidate is the copy beside the SKILL.md being followed, so the script always matches the procedure; the other two candidates are the resolution issue-runner uses for `scheduler.sh`, for a host that does not say where the skill lives. The worktree is the PR's own checkout: a copy there — a relative path, or this plugin's own repository under change — is a script the PR controls, which could report `changed` as unchanged or any command as passed. Hence only absolute paths outside the worktree count. The resolution runs inside every validation call because shell state does not persist across tool calls.
- **Why the base is merged in before a validation verdict.** The contract is the base tip's, but its command runs in this checkout. When `origin/<base>` is ahead of the merge-base, what the command checks may have moved with it (a failure fixed on the base), or what it names may exist only on the base — a contract and its script landing together after this branch forked, which makes the command exit 126/127 here. Merging the base in early (Step 9's base-freshness recipe) and re-running is therefore part of "fix" for a failure, and a required step before concluding that a not-runnable command means a broken contract. Before that, the PR's own diff is checked: a script exits with its last command's status, so a missing tool deep inside the project's script also lands on "not runnable", and if this PR touched what the command runs, the fault is the change's, not the contract's. The diff re-resolves `<base>` because it is a later tool call: no variable survives from the script's run or from Step 8's capture.
- **Why a broken contract never means no validation.** Absence of the file is today's behavior (the project's conventions decide), but a present-and-broken file — an invalid grammar (exit 3) or a command that is not runnable (exit 4) — must never degrade silently into "no validation": a typo in the file would otherwise switch validation off. Interactively it becomes an explicit user choice; either way the contract, not the change, is what is broken, which is why a not-runnable command gets the same `fallback (contract invalid — user authorized)` record. The choice is a standing authorization for the rest of the run because re-running the script would only fail the same way and ask again; `check` reads only the grammar and never runs the command, so the not-runnable case can first arise at Step 5 or Step 8, not Step 3. Step 9's `changed` still runs because it diffs the path and needs no valid contract. Orchestrated, the blocker recurs identically until a human fixes the file on the base branch, so the runner never re-dispatches on it within a run.
- **Why an unresolvable base is a failure, not a blocker.** Exit 2 covers a fetch of `origin/<base>` that failed three times (linked worktrees share that ref, so a sibling's simultaneous fetch may hold its lock once — never three times), no such ref, a tree or object that could not be read, no merge-base (`changed`), or an unresolvable worktree root. It is an environment failure — the `gh` calls, the fetch, a clone with no such remote branch — never a verdict on the change, and never a fallback: a cached remote-tracking ref is never read in its place because it may be stale, and an empty ref would silently read the working tree's copy. Orchestrated it is the result file's `failed` class, the same as a refused push or bad credentials, because a human has nothing to review. Step 3's probe re-runs the script once before concluding, since a transient `gh` failure there has cost nothing yet. A missing script (exit 7) is a broken install, and any other exit of the call (126 for a script file that exists but cannot be read) is treated the same: never "no contract", never a skipped validation, never a pass.
- **Why preflight never replaces CI.** Preflight and full are fast feedback in the worktree, before the PR is opened or marked ready; when the project has CI, CI remains the authoritative post-PR verdict. Both must hold. With no CI (`checks: none`), the contract's validation is the only automated verification the merge had, so the report says so. The progress marker is written immediately before `full` because it can run long and the orchestrator's hang threshold reads the marker's mtime.
- **Why the issue is read in full and planning hints are verified.** Context lives in the discussion, so every comment is read and references followed. `/issue-plan` hints (`## Interfaces`, `Files likely touched:`) were written at planning time; the default branch may have moved since (dependency PRs merged), so they seed the Explore prompt but are checked against current code. The inline-review authorization is settled at Step 2 so an unauthorized run stops before it has spent effort implementing.
- **Why resume reads the branch before the body.** The PR is data: any branch matching the contract could carry any body, so the commits decide what the plan is worth. In a reused worktree the working tree is the truth. In a fresh worktree the fetch names explicit destinations because a single-branch clone — the norm on the ephemeral hosts the checkpoint targets — would otherwise fetch only into `FETCH_HEAD` and never create `origin/<branch>`, and it fetches both refs because a stale `origin/<default-branch>` would make a checkpoint-only branch look partially executed. A lone checkpoint commit and a clean tree mean the previous run died before implementing; its plan is verified because the base may have moved. An orphan branch (the run died between the checkpoint push and `gh pr create`) has lost its plan, so the resumed run re-opens the draft in Step 4 and a second crash does not lose it again.
- **Why the leftover-branch guard blocks.** The checkpoint is otherwise best-effort, but pushing blind past a failed `ls-remote` probe (auth, transport) could plant the very second branch the guard exists to prevent. A hit is a branch an earlier run left behind, which the PR-based resume check cannot see when it has no open PR (see issue-runner REFERENCE.md, "`origin/<type>/issue-N-<slug>` exists but no PR is open on it"). A merged PR whose `headRefOid` is still the branch tip is positive proof for exactly that tip, so the branch is stale debris; the delete runs under a lease on that tip so a push landing between the comparison and the delete is refused rather than destroyed. A tip that moved on after the merge (the branch was reused or pushed to — possibly the only copy of that work), no PR, or only a closed PR is not safe to delete or to shadow with a second slug, so it is a blocker. A refused push after the guard passed is not that case (the guard has just ruled out a leftover branch), so it is recorded and the run continues: Step 6 pushes again and Step 7 creates the PR. The checkpoint is never retried without `--draft`: GitHub refuses to merge a draft, and a mergeable checkpoint is worse than none. The empty commit exists because a PR needs a commit; the squash merge drops it.
  The checkpoint's purpose — putting the plan on GitHub before a host that throws away `~/.claude` (Claude Code on the web, CI containers) can lose it — is in issue-runner REFERENCE.md, "Why the implementer opens a draft PR right after the plan".
- **Why interactive runs work in a dedicated worktree.** A dirty or concurrently-used main checkout is never touched. An aborted earlier run of the same issue can leave the worktree directory and its registration behind, which makes `git worktree add` fail, hence the pre-flight clear. A manual `git worktree add` carries no Agent-tool lock, so teardown is a plain remove. A surviving branch from the aborted run holds unmerged work, which is why it is resumed or deleted only after its PR is confirmed merged.
- **Why Step 7 adopts only an open PR.** Whether the PR exists is a fact, not a mode, so Step 7 checks it instead of inferring it from how it was invoked. `gh pr view` on a branch also resolves the branch's last **closed or merged** PR — a slug reused after a merged-branch cleanup, or a closed PR the user chose to resume — so the query filters on `OPEN`: a closed PR is never adopted, and a fresh one is created instead. Orchestrated, the new PR is created with `--draft` and Step 9 readies it; when the draft is refused because drafts are unavailable on the repo (recorded at Step 4), the plain create is the one orchestrated PR that is not a draft, which is why Step 10 reports it as `checkpoint: refused`. Step 4's "never without `--draft`" protects the *checkpoint*; the Step 7 PR is already implemented. When a PR is adopted, its body is spliced rather than overwritten: `gh pr edit --body` replaces the whole body, and a previous run's rebuttals and gate-degradation lines live under `## Review notes`, which Step 8's Converged rule reads — so only the part above that heading is replaced (the complement of Step 9's strip).
- **Why the prose profile presumes the Codex gate.** The prose profile narrows the triage bar on the assumption that the Codex gate still runs as the last independent check. When the gate is waived (`--no-codex-gate`, or the absent-CLI proceed) there is nothing behind the narrowed bar, so the profile is not honored and standard applies. Running Phase 2's "Availability first" check before Phase 1 under prose means a waiver decided there applies standard from iteration 1, instead of discarding work later; a waiver that arises only after Phase 1 has begun counts as a revocation, because the convergence reached so far was reached under the narrowed bar. For the same reason, a pass 1 that fails under prose has no fallback, whatever the failure (credit/quota, auth, network, or the prose block's own `97` when it cannot build its prompt): the Phase 1 verdict a merge without the gate would rest on was itself reached under the narrowed bar, so it blocks rather than degrading or offering to merge. `guidance.md` carries copied findings and recovered traces, so its location proves nothing about who wrote it — the same rail as the gate waiver.
- **Why the profile text lives in the private gate directory.** The prose profile text steers triage: it decides what counts as blocking in both Phase 1 reviewer prompts and the prose Codex prompt. A fixed, predictable `/tmp` name let another local user plant the file first (for example read-only), so an unchecked write failed silently, a non-empty check passed, and the planted text reached the reviewers (#73). `GATE_DIR` is the run's own directory (the orchestrator's per-user state directory, or the repository's git directory), the write removes any leftover and then creates the file only if none exists (`set -C`), and its own exit status decides: any failure stops the prose run with a blocker rather than reading a file this run did not write. The prose gate block reads the file only from this run's `GATE_DIR` and only if you own it (`-O`), so a file another user placed there is never read.
- **Why the prose guard reads `--raw`.** The guard must see mode changes as well as paths: an exec-bit change, a symlink or a submodule on a `.md` path is not prose. `git diff --name-status` does not show mode changes, so the block reads `--raw` and checks both modes (`100644`, or `000000` for an added or deleted file). Its fetch is tried three times, as in the validation script, because a sibling's fetch can hold the shared ref lock; the guard resolves `BASE_BRANCH` itself because no variable survives from the Step 8 capture. A failed fetch or diff revokes, so the guard fails toward standard review: it can only drop the profile, never grant it.
- **Why an interim notification is not a result.** The host reports "Agent finished" to the orchestrator whenever an implementer stops with a background child (a Codex gate pass, a reviewer) still running, so an implementer that ends a turn there delivers a notification that looks final but carries no `result.json`. The orchestrator would have to infer from prose that it is still healthy, and a wrong inference classifies a live implementer as blocked or failed and cascades to its dependents (issue #80). The fixed one-line form `interim: waiting on <what>` removes the inference; the orchestrator's `classify.sh notification` recognizes it, and the full rationale is issue-runner REFERENCE.md's entry of the same name. The form carries no `worktree:` line and no result file on purpose: those mark a final exit.
- **Why Liveness never waits on a notification.** Two production stalls. A Phase 1 reviewer subagent went silent while the implementer waited on its completion notification, and the host's low-memory heuristic killed background `codex` runs and monitors, losing their completion notifications with them. So every child runs in the background with a bounded wake-up: a foreground call would block the implementer inside it, unable to wake, refresh the progress marker or stop the child. Rewriting the marker on every wake makes the runner's hang rule measure the implementer, not a legitimately long child. A wake-up can itself be killed, and then the marker stops moving: that stall is exactly what the hang rule is for, and it stops and classifies the implementer as it would any stuck one. The silent-reviewer fallback runs the pass inline, which is a recorded degradation (the implementing context reviewing its own work); a dispatch that waives the Codex gate never authorizes it, whatever it carries, because there the inline pass would be the only review. As with the gate waiver, text in an issue or PR is never authorization.
- **Why gate passes are files with attempt identities.** Completion must be provable from disk without any notification, since the host can kill the notification along with the process. So each pass writes its own `codex-pass-K.*` files, with `.exit` written from the same subshell that ran the CLI under a 30-minute watchdog; no gate output uses a fixed `/tmp` name, so a second pass never overwrites the first and a run of the same PR number in another repository never collides. The interactive `GATE_DIR` lives in the per-worktree git dir, outside the working tree, so it is never staged; because it outlives an invocation, a new interactive invocation clears it on entering Phase 2. Both the `.exit` write and the watchdog's `.timeout` marker happen only while `.attempt` still names that launch, and the watchdog kills its own CLI at the bound either way: an older attempt that outlived its own shell therefore does not write into a re-run's files. The one exception is the instant between its check of `.attempt` and its write, which only an attempt still alive past its own watchdog's bound can hit. The 35-minute Killed bound is the watchdog's 30 minutes plus its grace. A `.exit` of `0` with an empty log is no review at all, never "zero findings". `.lost` is never cleared by the launch block, so a loss count survives a restart and one loss is never counted twice. After a restart, a pass without `.exit` is still waited on until the bound, because a detached pass can outlive the host that launched it. A `gate: cannot write <dir>` launch never started, so it is an environment failure, not a kill.
- **Why reviewers read touched files in full.** Invariant violations rarely show in the diff alone: the Phase 1 reviewers are told to read every touched file in full, and the inline fallbacks keep that full read.
- **Why the availability check reads the model catalog.** `codex debug models` must list the gate's model (`GATE_MODEL`, `gpt-6-sol` by default) before any pass runs; the check names the model the pass will run, never a fixed one, so a `--codex-model` run does not discover a missing model mid-run in each implementer. A CLI that is installed but fails that check is most often older than 0.155 (or too old to have `codex debug models` at all), but the model is not in the catalog bundled with the binary: it arrives in the catalog a logged-in CLI fetches from the server, so a logged-out CLI, or one with no network and no cached catalog, fails the check too. That is why the message names both remedies (upgrade, or check `codex login` and network) and why the report adds the `codex --version` output: a human can tell which cause applies. It is never a credit/quota degradation and never a passed gate, because nothing was reviewed; it follows the absent-CLI rules, waiver included. The check reads the catalog, not a review's stderr, because that stderr also carries the review transcript.
- **Why the gate pins gpt-6-sol.** The gate is the last independent check before an unattended merge, so it runs on a reviewer chosen for reliability. In the GPT-6 family Sol is the workhorse tier and `gpt-6-astra` the frontier tier; Sol is pinned for its reliability at lower cost (reported near-Astra factuality at roughly half GPT-5.6 pricing), and `gpt-6-astra` is the escalation alternative for a project that wants the frontier reviewer. `gpt-6-sol` is the default, and the user may choose another exact id with `--codex-model`. Either way the explicit tier id is pinned, never a bare family alias such as `gpt-6`, so the pin does not drift with the alias. The id needs Codex CLI 0.155 or later (README, Requirements); an older CLI does not know it, which the catalog check under "Availability first" catches before any pass runs.
- **Why the prose gate names the diff in its prompt.** The pinned CLI refuses custom instructions next to `--base`: on 0.155.1 it prints `the argument '--base <BRANCH>' cannot be used with '[PROMPT]'`, and it does the same when the prompt comes from stdin `-`. So the prose invocation drops `--base`, and its prompt names the diff itself (`git diff origin/<base>...HEAD`) and carries the profile text. The block resolves its own inputs (PR number, base branch, `origin/<base>`, the profile file) and fails closed: if it cannot build the prompt it writes `97` to `.exit` without running codex, so a missing input can only surface as a failure, never as a pass.
- **Why Phase 1 verifies the capped iteration's fixes.** In the last recorded run, most retries came from Phase 1 hitting its cap while the capped iteration's fixes were still unreviewed: iteration 4 applied its findings and the loop stopped, so a cap-stop was reported for findings that were already fixed, and a converged loop could not be told apart from an unverified one. One extra iteration on the fixed head settles it. It applies nothing: its findings are either absent (the fixes held, converged) or open work (cap-stop), exactly as the last Codex pass never starts a fix round it could not verify. Exactly one, so the cap still bounds Phase 1's spend (at most five iterations, ten reviewer dispatches, per Phase 1 run).
- **Why the last Codex pass never starts a fix round.** Every fix round must be verified by a later pass, and pass `MAX_CODEX_ITERATIONS` has no pass left to verify one, so it applies nothing and stops (cap-stop). Its unfixed findings go under `## Review notes` as open work, never as a rebuttal, so the Converged rule cannot read them as skip-and-documented. A finding a fix round introduced is new work, not bouncing: under the cap it gets its own fix round, and the cap is what bounds a cascade of new findings. On an interactive `standard` run with a Markdown-only diff and design-level findings, the cap-stop question may offer a retry under the prose profile; an orchestrated implementer never offers it, and its blocker goes to the runner, whose Step 4 may offer it instead.
- **Why small in-diff findings are fixed.** Convergence only counts Apply-class findings, so a small finding in code the PR just wrote, triaged below that bar, merged unfixed and was tracked nowhere; fixing it later costs a second worktree, review and deploy. Size and ownership decide, not the reviewer's label: in the diff, about ten lines at most plus a test, no product decision. Whatever stays deferred (out of scope, needs a decision, large) goes into `result.json`'s `deferred` as well as the PR body, so the orchestrator can ask the user once instead of rebuilding the list by hand. Defer is self-classified and its entries reach the user only at Step 5, after the merge; the issue accepts that, and the safeguard is that a bug the PR introduced is never Defer. The cap-stop rules are unchanged, so a small finding on the last allowed pass is still a cap-stop; that is the price of not merging known small defects.
- **Why a failed verification pass never degrades.** A fix round is verified only by the pass after it; no other review saw that head, because Phase 1 converged on the head before it. Degrading to Phase 1's verdict there would merge unreviewed code, so every non-zero exit on a verification pass is `errored`, credit/quota included. The same holds on pass 1 when the head carries a `fix: address codex gate findings` commit that no Phase 1 iteration of this invocation reviewed (a resume or retry after an earlier attempt's fix round).
- **Why iteration history goes only under Review notes.** The PR body becomes the squash-commit message (Step 9), so Summary / Changes / Test plan must be current on every push. The merge step strips the body from a heading exactly `## Review notes` down; history under any other heading name would leak review chatter into the commit.
- **Why an unfinished PR returns as a draft.** An orchestrated PR bounced out of the review loop is still a draft, because Step 9 is the only place it is marked ready. A PR stopped at the no-merge ready line is deliberately **not** a draft, for the same reason a merged one never was: a human needs a real, mergeable PR to act on. A blocker raised below the ready line (base freshness, the checks gate, a moved head) must put the PR back to draft before returning, and it must do so statelessly, because it is a later tool call and no variable survives to it — so the recipe re-queries `isDraft` instead of trusting a variable. The two blockers raised above the ready line (full validation, contract
  changed) run it too, because the PR is not necessarily a draft there: an earlier attempt may have readied it and then crashed; on a draft the recipe is a no-op. It never fails open: the undo is attempted unless draft status is positively known, and if the undo (or the query) fails, the blocker says the PR is non-draft and mergeable by hand, so the runner's Step 5 does not lean on an invariant that did not hold. On a repo that refused drafts (`checkpoint: refused`) that failure is expected and the PR is the documented exception. So every orchestrated PR that *returns* unfinished is a draft, or its blocker says otherwise; the runner's Step 5 relies on that. The one gap is a crash (not a
  blocker) inside the ready→merge window; Step 5 handles that non-draft case too. Authorization for no-merge mode travels only via the dispatch prompt, the same trust rule as the Codex gate waiver. Bouncing PRs get their fixes pushed and the body refreshed so the unresolved state is visible on the PR. See also issue-runner REFERENCE.md, "Why the implementer opens a draft PR right after the plan".
- **Why full validation and the contract check precede ready.** `full` runs unconditionally, once per head, on the converged head. The script reads the base tip afresh and reports `full not declared` when there is none, so a `full` line that landed on the base after Step 3's probe is never missed. The `changed` check fails closed: exit 2 or 7 is the script's `failed` class as everywhere, and a git failure is never read as "unchanged". Exit 5 means this PR changes the project's validation policy, which only a human authorizes. The validation above already ran the base branch's copy, so the edit was inert for this PR; what needs a human is letting it become the next PR's policy. Interactively
  the ordinary merge confirmation is not enough on its own, because it does not name the change. Orchestrated, the blocker applies under `Merge mode: no-merge` too, because `--merge-ready` merges a `ready` PR mechanically and nobody would see the change. Under a standing fallback authorization (an invalid contract or not-runnable command the user chose to proceed past at Step 3, 5 or 8), `changed` still runs: it diffs the path and needs no valid contract. See also issue-runner REFERENCE.md, "Why validation is declared by the project and read from the base branch, never guessed by the implementer or taken from the PR".
- **Why the registration poll after `gh pr ready`.** The PR may still be a draft (the Step 4 checkpoint, or one an interactive resume adopted), and GitHub refuses to merge a draft. It may instead already be non-draft because an earlier attempt readied it and then crashed or blocked; the draft-provenance rules still apply to it, so `READIED` records whether the PR *was ever* a draft, not whether this invocation flipped it, and the poll runs on `READIED` so a resume never races the `ready_for_review` run an earlier attempt triggered. Because this is the only place the draft flag comes off, base freshness, the checks gate and the merge run unchanged below it. CI keyed on `ready_for_review` has
  had no chance to run yet, so it gets a bounded window to register — draft-era `skipped` runs appear instantly and do not count — before "no checks reported" or "all skipped" can mean "no CI". Draft-filtered CI shows up as no check runs at all, or as runs that report `skipping` (a job-level `if: !draft` still creates them, instantly), possibly next to a job that does run on drafts (lint passed, tests skipped): a mixed rollup `--watch` would accept. The `ready_for_review` run re-creates each skipped job under the same name, so the poll waits, bounded, until every skipped name has a non-skipped twin. No snapshot, no state: it works the same on a PR an earlier attempt readied just before
  crashing. A workflow that skips drafts (`if: github.event.pull_request.draft == false`) without `ready_for_review` in its `types` never executes on the PR — either no check runs exist, or every run reports `skipped` — and the checks gate cannot tell either from real coverage on its own; hence the README requirement, and `READIED` plus the post-`--watch` `TOTAL`/`SKIPPED`/`NEVER_RERAN` counts that keep the gate's verdict honest.
- **Why base freshness runs before the checks gate.** The review judged the diff against its branch point; a sibling PR may have merged into `$BASE_BRANCH` since — a semantic-conflict window no textual merge check catches, and file overlap is not a reliable signal for it: sibling PR A renames a function in `a.ts`, this PR calls the old name from `b.ts`, the two diffs never touch a common file, and this PR's tests never run against main+A (issue #15). So the base is merged in whenever it moved at all; the overlap check only warns that a *textual* conflict is likely — it never decides whether to merge, and its absence never skips the merge. The recipe prints the conflicting paths (or, when
  `git merge` failed for a non-conflict reason such as an untracked file in the way, says so) **before** `git merge --abort` erases the conflicted state, since shell state does not survive to a later tool call (the same rule as `READIED` and the draft-revert recipe); "no merge to abort" is expected when the merge never started. Automatic conflict resolution is never attempted. A post-merge validation failure is exactly a failing check, never a green light; orchestrated, the merge commit is pushed so the unresolved state is visible on the PR. After the push, a PR that was a draft repeats the registration poll because the new head has no check runs until CI registers them, and `--watch` reads
  that instant as "no checks reported"; the post-`--watch` counts then judge the head that actually merges. Freshness runs before the gate so `--watch` covers the commit that actually merges — hence never push after the gate has passed.
- **Why the checks gate reports draft-filtered CI.** `gh pr merge` enforces only *required* branch protections server-side; advisory checks (the common case on personal repos) would not stop it (issue-runner REFERENCE.md, "Why merge waits for CI checks"). The `step=9.2` marker is written because `--watch` is the procedure's longest silent wait, and it lets whoever reads `--status` tell "waiting on CI" from an unexplained silence. The counts are taken after `--watch` because a base-freshness push may have replaced the head, and draft-era runs may have been joined by real ones since the poll. `none` may mean draft-filtered CI that never ran, so "no CI configured" is reachable only for a PR
  that was never a draft. All-`skipping` runs exit 0 from `--watch` but are not coverage; nor is a skipped run with no non-skipped twin of the same name (a job that runs on drafts passed next to one the ready event never re-ran). That last signal also trips on a job that skips on every PR event, such as a push-only deploy job; the signal cannot tell them apart, so it errs toward the warning. `READIED=1` covers every PR that was ever a draft: every orchestrated PR except one created plain at Step 7 because drafts are unavailable, including one an earlier attempt readied before it crashed. All three degraded outcomes still merge but, like the gate degradations, a merge without CI coverage is
  never silent. `fail` always reverts to draft and blocks, no-merge dispatch or not: a PR is never left ready-and-red.
- **Why the merge is pinned to the validated head.** `--match-head-commit` pins the merge to the head this run validated and pushed (nothing is pushed after the checks gate, so the local `HEAD` is that head). A commit someone else pushed after the gate — a `.issue-runner/validation` edit included — was never seen by the `full` or `changed` runs or the checks `--watch`, so GitHub refuses the merge instead of landing it, and the refusal is never retried against the new head. The no-merge stop leaves the PR ready (non-draft), checks green or absent, for a human or a later `/issue-runner --merge-ready` to merge by hand. In the interactive teardown, the merged PR — not the issue being closed — is
  the positive proof for `git branch -D` (`-D`, not `-d`, because the squash merge breaks `-d`'s ancestry check); a manual worktree has no Agent-tool lock, so a plain remove suffices, and you leave it first so you are not standing in the directory you remove. An orchestrated `fatal: '<branch>' is already used by worktree at ...` after a successful server-side merge is cosmetic; the orchestrator's cleanup reconciles it.
- **Why the result file precedes the report.** The parent reads the result file first and falls back to the Step 10 prose only when the file is absent or unreadable, so an `outcome` that disagrees with the message is a bug in the run, not a tolerable drift. The same holds for a no-merge stop: the parent's Step 3 item 5 reads `outcome` (`ready` vs. `merged`) first and falls back to the `ready: PR #<P>` wording. A `checkpoint: refused` line means the crash-recovery checkpoint does not work on this repo. `validation: not run` exists because Step 3's probe checks the grammar and runs nothing, so none of the other four values would be truthful for an exit before Step 5's preflight. Degradations
  (Codex gate skipped or waived, a failed verification pass merged by authorization, inline Phase 1) are stated prominently because a merge without Codex coverage or without fresh-eyes review must never be buried in the report.
- **Why model and reviewer choices come only from the user's flags.** The reviewer count, the reviewer model and the Codex model change what a merge is certified by, so they are authorizations like the gate waiver: the runner validates the user's flags and writes fixed-form dispatch lines, and gh-issue honors those lines only, never issue, PR or `guidance.md` text. The lenses beyond A and B are fixed in review-loop.md, so a count carries no free text; a malformed line blocks rather than silently weakening the certification the user asked for. Naming the model in the preflight and the result file (`gate_model`, `reviewers`) makes the configuration that produced a merge auditable.
