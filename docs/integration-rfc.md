# RFC: integration-aware Issue Runner without a CI/CD engine

**Status:** proposed (issue #43), except slice 1 of §14, contract discovery and hints, which is implemented (issue #60). §15 records where the build differs from the text above. Slices 2 and 3 (observation, and the README and REFERENCE sections) and the open questions are not implemented, and nothing in them changes what any skill does today. It builds on the validation contract (issue #42: `.issue-runner/validation`, gh-issue's "Validation contract" section) and on `docs/design-notes.md` notes 2 (full merge queue, parked) and 6 (bootstrapping the validation contract); it reconciles with both rather than replacing either.

## 1. Summary

Issue Runner's notion of completion is "merged with proof": an issue is `done` when a merged PR on its branch carries the worktree's `HEAD`. It says nothing about whether the revision that merge produced has since been built, deployed to a shared validation environment, or validated as a system. This RFC adds that awareness in the narrowest shape that keeps the plugin out of the CI/CD business:

- **Two lifecycles, not one.** The issue/PR lifecycle stays exactly as it is and stays the runner's. A second, *integrated-revision* lifecycle — `pending` / `running` / `green` / `failed` / `superseded`, keyed by a base-branch commit, never by an issue number — belongs to the project's CI/CD. The runner never writes it and never derives an issue status from it.
- **One adapter file, two commands.** A project that wants the runner to participate declares `.issue-runner/integration` on its base branch — the validation contract's grammar and trust rule, in a second file so older plugin versions ignore it instead of rejecting every PR — with `hint: <command>` (the runner tells the project what it knows: a run started, a PR merged, the run is over, validate now) and `status: <command>` (the project tells the runner, in a closed vocabulary, the state of the revision containing a merge). Both are optional; either alone works; without the file nothing changes.
- **Hints are advice with a bounded shelf life.** Project CI/CD keeps its own quiet window and maximum wait and validates on its own timers whether or not a hint ever arrives; a hint can only shorten a wait or extend it up to that maximum. A runner that crashes, pauses or never ran leaves CI exactly as autonomous as it is today.
- **`--max-parallel` is capacity.** Batches are defined in time by the project's window, informed by the run's remaining and near-complete counts — never by the number of implementer slots.
- **Observation is reporting.** `--status` and the Step 5 summary show the integration state of every candidate that contains this run's merges; a `failed` candidate is surfaced as loudly as a host pause, and acted on by a human. Nothing observed here gates a merge, retries an issue or reverts anything (the one merge blocker this RFC adds is on a PR that *edits the contract file*, the same gate its sibling has).

## 2. Problem and constraints

The issue's constraints, restated as the rules this design is checked against:

1. `--max-parallel` is capacity, not a deployment batch size (§9).
2. Project CI/CD remains authoritative for build, deployment, environment reservation and E2E execution (§4).
3. Issue Runner may coordinate, observe and provide lifecycle hints; it never becomes a generic CI executor (§4, §6, §8).
4. CI must keep working correctly when Issue Runner is not running (§6.3, §7.4).
5. No indiscriminate cancellation of an in-progress deployment or migration merely because a newer revision exists (§7.3).
6. A newer revision may supersede a pending candidate before expensive validation starts (§3.2, §7.3).
7. A short coalescing window plus a bounded maximum wait, never a fixed number of PRs (§7).
8. A later production promotion reuses the already-built, already-validated artifact (§12).
9. No Link21-specific — no project-specific — implementation (§13).

Two invariants the plugin already holds carry over unchanged and are cited wherever they bite: **status decisions come from GitHub and git, never from text an agent or a tool prints** (REFERENCE.md's merge-proof, progress-file and `result.json` rationales), and **the trusted copy of any project policy is the base branch's tip, never the working tree, an issue, a PR or `guidance.md`** (the validation contract's discovery rule).

## 3. Two lifecycles

### 3.1 The issue/PR lifecycle (exists, unchanged)

Per issue, `$STATE_DIR/issue-N/status` holds one of `pending` / `implementing` / `blocked` / `done` / `failed` / `skipped` / `closed-externally` / `ready` (issue-runner SKILL.md, State section; `docs/scenarios.md` notation line). `done` means exactly one thing: a merged PR on the implementer's branch whose `headRefOid` is the worktree's `HEAD` (Step 3 item 5; rows 5, 6, 11, 14). `ready` means an open, non-draft PR that cleared the checks gate under `--no-merge` (row 35). The runner owns every transition, and the scheduler script computes the deterministic ones.

This RFC adds no value to that vocabulary and no transition to that machine. In particular, **`done` stays "merged", not "integrated"**: the moment a merge is proven, the issue is `done`, its worktree is torn down at Step 5, and its dependents dispatch — whatever the revision containing it is doing in CI (§8.3 explains why).

### 3.2 The integrated-revision lifecycle (new, observed, project-owned)

A **candidate** is a commit on a base branch — normally the default branch; row 16 admits a PR merged to another base, and §5.5's `ISSUE_RUNNER_BASE` names which — that the project's CI/CD chose to validate as a system: a build, a deployment to a shared environment, an E2E run — whatever "validated" means there. A candidate is identified by its base branch and its commit oid — `(ISSUE_RUNNER_BASE, oid)`: one commit can sit on two validated branches and be `green` on one while `pending` or `failed` on the other, so the adapter's records, the `merged` dedupe key (§6.2) and the runner's grouping (§8.2) all carry the branch — and by nothing else: not by an issue number, not by a PR, not by a run. A candidate normally contains several merges (§7), possibly some made by hand (§10).

States, the closed vocabulary the `status` command speaks (§5.4):

| State | Meaning | Who moves it there |
|---|---|---|
| `pending` | The revision is the current tip-in-waiting: it will be validated once the project's quiet window closes, unless a newer revision replaces it first. | CI, on a push to the base branch |
| `running` | Validation of this revision is in progress (building, deploying, testing). | CI, when the window closes or on a `flush` |
| `green` | Validation of this revision passed. | CI |
| `failed` | Validation of this revision failed. | CI |
| `superseded` | A newer revision replaced this one — before its validation started, or, under the project's own cancellation policy (§7.3), while it was `running` but before any phase the project deems unsafe to abandon; either way the newer candidate is the one to look at. | CI, on a newer push while this one was `pending`; or on a cancellation its own policy allows while this one was `running` |
| `unknown` | The adapter has no record of this revision (too old, never a candidate, before the adapter existed). | the adapter, on a query |

Transitions: `pending → running`, `pending → superseded`, `running → green | failed`, and `running → superseded` for one outcome only: a cancellation the project's own policy allows (§7.3). The RFC recommends — and only recommends, since this is the project's policy (§4) — that `running` is never superseded: constraint 5. A project that knows its early phases are cheap to abandon may cancel a `running` candidate before its deployment starts; that is its adapter's decision, invisible to the runner, which only ever sees the resulting state — `superseded`, the same state as a candidate abandoned while `pending`, because the same thing is true of it: nothing of it was validated and a newer candidate replaced it. A cancellation that leaves anything behind — a half-applied migration, a reserved environment — is the project's to report as `failed`, never as `superseded`.

The runner reads these states through `status` and writes what it read to `$STATE_DIR/issue-N/integration` (`<state> <candidate-oid> <ISO-8601 UTC timestamp>`, one line, written at Step 5 under the run lock — `--status` only prints, §8.2). That file is **informational only**, exactly like `progress`: its content is never an input to a status decision, never merge proof, never a reason to retry, and a stale or missing one changes nothing about the run.

### 3.3 How the two relate

Many-to-one, and in both directions:

- Several issues' merges land in one candidate (coalescing, §7). The per-issue view is *the newest candidate containing this issue's merge commit whose validation is in progress or finished* (a `pending` one only when there is no other, §5.4): a `merged` revision whose own state is `superseded` is followed (bounded, §5.4) to the candidate that replaced it, because that candidate contains the merge too.
- One issue's merge appears in every later candidate. Its "integration state" therefore has a time dimension the issue state does not: `green` today, `failed` after an unrelated merge tomorrow. The runner reports the state at the time it looked, timestamped, and says how to look again (`--status`).

| | Issue/PR lifecycle | Integrated-revision lifecycle |
|---|---|---|
| Unit | one issue, one PR, one branch | one base-branch commit |
| Owner | Issue Runner (statuses written under `$STATE_DIR`) | project CI/CD (state kept by its adapter) |
| Proof | GitHub + git (`headRefOid == HEAD`) | the project's own validation |
| Terminal for the run | `done`, `failed`, `skipped`, `closed-externally`, `ready` | none — a candidate can be `green` and later replaced |
| Drives dispatch | yes (the scheduler's ready set) | no (§8.3) |
| Reported | summary table, `--status` | summary "Integration" section, `--status` |

## 4. Responsibility boundary

**Project CI/CD owns**, and this design never touches: triggering on pushes to the base branch; building; choosing, reserving and releasing environments; deploying; running E2E or any other system validation; deciding what a candidate is and when its window closes; cancellation and supersession policy; retries of its own jobs; promotion; and the store that remembers candidate states. It runs the same with or without the runner.

**Issue Runner owns**: knowing which merges belong to a run and where the run is in its lifecycle (how many issues may still merge, which are about to), telling the project that — hints, §6 — through a command the project declared; asking the project, through another declared command, what happened to the revisions its merges landed in; and reporting the answer. It never runs a build, deploys, waits for an environment, cancels a job, or holds integration state of its own beyond what it last observed.

The line is the same one the validation contract drew for tests: the plugin runs a project-named command and reads a narrow, fixed-shape result (there: an exit status; here: an exit status for hints, one line from a closed vocabulary for status). Lint, unit tests, builds, containers, E2E, Docker, Kubernetes, Playwright, GitHub Actions, GitLab CI — named here only to say they are all the project's business and none of them appears in the contract.

## 5. The adapter contract: `.issue-runner/integration`

### 5.1 Grammar

```
# .issue-runner/integration — how this repository's CI/CD hears from, and answers, Issue Runner
hint: ./scripts/ci/issue-runner-hint.sh
status: ./scripts/ci/issue-runner-status.sh
```

The validation contract's grammar, verbatim: `key: <command>` lines, `#` comments and blank lines; anything else — a stray line, a duplicated key, a comment-only command, CRLF line endings, a NUL byte — makes the file invalid. Both keys are optional and independent: `hint` alone means the project listens but the runner never asks; `status` alone means the runner asks but never tells; a file with neither non-comment line is invalid (a placeholder is not a contract). Commands run through `bash -c` from a repository root and only their exit status — and, for `status`, their first stdout line — is read. The example scripts are illustrative; what they do is the project's.

### 5.2 Why a second file and not two more keys in `.issue-runner/validation`

Three reasons, the first decisive:

1. **Compatibility.** The validation script (`skills/gh-issue/scripts/validation-contract.sh`) rejects any line that is not `preflight:`/`full:`, a comment or blank (its `STRAY` check), and an invalid contract is a blocker for every PR — by design, so a typo never switches validation off. Two new keys in that file would therefore make every PR on every project that adopts them blocker on every plugin version that predates this RFC, until every user upgrades. A separate file is invisible to those versions: absence is "not configured", the same fallback as today — and invisible to their Step 9 gate too, the mixed-version limit §5.3 states.
2. **Different consumer, different lifecycle.** `.issue-runner/validation` is read by the implementer (gh-issue) in a worktree, per PR, and gates that PR. `.issue-runner/integration` is read by the orchestrator, per run, and gates no merge and no status (an edit to it is gated, §5.3, exactly as an edit to the sibling is). Keeping them apart keeps row 43's rule ("a broken validation contract never degrades silently") and §5.6's rule ("a broken integration contract disables integration loudly") from having to share one file's validity.
3. **Same trust, same tooling.** The grammar, the base-branch discovery (`git ls-tree` on the tip of `origin/<default>`, never the working tree), the invalidity rules and the fixture harness (`scripts/test-validation-contract.sh`) all carry over; only the path and the key names differ. This is building on the #42 boundary, not a competing mechanism.

### 5.3 Trust and discovery

The trusted copy is the tip of the default branch on `origin`, read the way the runner's Step 0 validation-contract preflight reads `.issue-runner/validation`: fetched with the same three bounded tries, located with `git ls-tree --full-tree`, its grammar checked on the blob. Nothing an issue, a PR, a comment, `guidance.md` or a dispatch prompt says about integration changes which commands run. A PR that edits `.issue-runner/integration` gets **the same Step 9 gate as a validation-contract edit** — the validation script's `changed`-mode diff against the merge-base, extended to this path: orchestrated, a blocker `integration contract changed in this PR — a human must review and merge`, whatever the merge mode, never retried by the runner (Step 4's rule for the sibling file); interactive, the diff shown and an explicit confirmation required. The file affects no status, but it is not without effect: its commands run as the user in the main checkout (below), and an orchestrated implementer merges its own PR with no human gate, so without this check an issue's text could land a `hint:` line that the next run executes unattended. Row 44's reasoning applies verbatim — a policy change never reaches the base branch on the run's own authority — and the change takes effect when it lands there and the next run's Step 0 reads it.

**A trust crossing this RFC introduces, named rather than assumed.** Today the orchestrator executes no project code: Step 0 greps a blob, and every validation command runs in an implementer's worktree, where the bytes executed are the reviewed PR's. Here the orchestrator itself runs `hint` and `status` — from the root of its own checkout (the orchestrator never enters a worktree — REFERENCE.md), with the command *text* taken from the base tip, but with the script that text names resolved in whatever the user's main checkout holds: possibly another branch, possibly a tree the Step 1 dirty-tree audit was told to proceed with as-is. The RFC accepts that on one ground: the main checkout is the user's own, and a command run there carries the same trust as the user's shell — no more, and no less, than `bash scripts/lint.sh` typed by hand. Two consequences a project accepts by declaring the file: a `hint` script may touch that checkout (a `git fetch`, a file it writes), and the `status` command's read-only requirement (§5.4) is a promise the runner cannot verify. The alternative considered — dispatching a `general-purpose` subagent to run each command from a clean checkout of the base tip, the `--merge-ready` refresh's pattern — was rejected for hints: an agent per hint is far too expensive for a fire-and-forget line, and a clean checkout does not change whose code runs, only where. What the gate above buys, stated exactly: nothing an issue or PR says can put a command *line* in this file — the line was merged by a human — on a run of a plugin that carries the gate. The gate lives in the *merging* plugin, so on the mixed-version population §5.2 assumes, an orchestrated runner that predates this RFC merges a PR that adds or redirects this file as an ordinary diff (the gap a pre-#42 runner has for `.issue-runner/validation` today), and the next upgraded run trusts the base copy it left. A project that needs the line-level boundary before every merge-capable runner on the repository is upgraded protects `.issue-runner/` with repository-side review — CODEOWNERS or branch protection — which the plugin cannot supply. The script that line names is not covered: as with the validation contract (row 44's carve-out), a PR that edits what the command executes is an ordinary diff for the Step 8 reviewers, and an orchestrated implementer merges such a PR itself. So on a project that declares `hint:` or `status:` and runs orchestrated with merge authority, README's "Trust the issue authors" limitation extends from merge authority to unattended execution in the orchestrator's checkout; `--no-merge` is the mitigation there as it is for the limitation itself — a human reads the script edit before `--merge-ready` merges it. The gate still earns its place: it stops an issue from *enabling* integration on a project that has none, and from redirecting an existing line — that, and no more, is what it does, on a run of a plugin that carries it.

### 5.4 The `status` command

Called with its own, smaller environment — the §5.5 table marks each variable's presence for `status` in its "Present for" column: `ISSUE_RUNNER_HINT_VERSION`, `ISSUE_RUNNER_BASE`, `ISSUE_RUNNER_REVISION=<oid>` (the merge commit whose integration state is asked for — required), and `ISSUE_RUNNER_RUN` / `ISSUE_RUNNER_INVOCATION` (the run's values when the query runs inside a run — Step 5; `none` from a standalone `--status`, which skips the State block). `ISSUE_RUNNER_HINT` is **absent**, which is how an adapter tells a query from a hint. It must be read-only and quick (bounded: the runner abandons it after the §5.5 bound `N` and reports `unavailable`). Its first stdout line is:

```
<state> <candidate-oid> [<detail…>]
```

`<state>` is one of `pending` / `running` / `green` / `failed` / `superseded` / `unknown` (§3.2). `<candidate-oid>` is the **newest candidate on the queried `ISSUE_RUNNER_BASE` containing the queried revision whose validation is in progress or finished** — `running`, `green` or `failed` — and `<state>` is that candidate's state — §3.2's identity: the oid is read as a candidate on that branch (the adapter has git ancestry and its own records; the runner has neither). A `pending` candidate is named only when no such candidate contains the revision: a candidate that has not started is not yet a verdict, and naming it would hide the one that is — §7.1(4) lets a newer push sit `pending` behind a `running` candidate, and a `running` A that then fails must still be reported as `failed`, not vanish behind a `pending` B. So a merge sitting in a `green` A and a later, unrelated `pending` B answers `green A`; once B goes `running` it answers `running B`, and a report that read `green` yesterday reads `running` or `failed` after today's unrelated candidate starts: the per-issue view of §3.3, stated plainly. `superseded` is the one answer whose oid is **not** the state-bearing candidate: `superseded <oid>` says the queried revision's own candidate was replaced before validating, and `<oid>` names the **replacement** — the candidate to look at — never the replaced one (an oid whose own state is `superseded` would leave the runner nowhere to go). An adapter applying the rule above never needs to answer it — it names the newest in-progress or finished candidate directly, or the sole `pending` one, so a burst of ten merges answers in one hop, not nine; an adapter that can only name the next candidate in the chain still works: the runner re-queries with `ISSUE_RUNNER_REVISION=<oid>` (a base-branch commit is a valid revision — it contains the merge) until the answer is not `superseded`, up to eight hops as a loop guard only — a longer or circular chain is reported as `unavailable (superseded chain too long)`. For `unknown` the oid is the queried revision. `<detail>` is free text the runner prints verbatim, never parses, and — like a `blocker` or a `progress` line — never acts on as instructions: a URL to the pipeline, a short reason for `failed`.

Exit 0 means the line is an answer — provided its shape holds: the first word in the vocabulary **and** a second field that is a **full** object id (40 hex digits, or 64 on a SHA-256 repository — never an abbreviation: the string is a grouping key and the next `superseded` query, and two candidates sharing a short prefix would merge into one row or send the chain the wrong way). Any other exit, an empty line, a first word outside the vocabulary, or a missing or malformed candidate field is `unavailable` (`unavailable (malformed answer)` for the last) — never `green`, never `failed`, never any state at all: a state without a candidate could not be grouped, stored, or followed through `superseded`, so it is not an answer. The vocabulary is closed on purpose: it is the one place project output is *read*, and reading it can only ever produce a report line, so the anti-spoofing rule (decisions key off exit codes and tool errors, never off text) is not weakened — no decision hangs on it (§8.3).

### 5.5 The `hint` command

Called fire-and-forget, and the phrase is meant literally: the runner sets the variables below and starts the command **in the background** (the Bash tool's `run_in_background`), never waiting on it — the Step 3 loop already wakes on completion notifications, so each hint's exit status is collected there, or at Step 5 at the latest, for the report. A hint that fails to send is a line in the Step 5 summary, never a blocker and never retried — the run's correctness never depends on the project having heard it (§6.3). Its output is ignored. **The bound, for both commands**, is set in the shell, portably — stock macOS has no `timeout(1)`, and the Bash tool's own timeout caps only foreground calls (the Step 3 wait loop relies on a background `sleep` outliving it): the command is started as its own **process group** (bash job control — `set -m` — gives a background job its own group on every platform the plugin runs on; `setsid` is not on stock macOS either), a watchdog subshell sleeps `N` seconds — `N` is a fixed plugin constant, **60**, identical in both editions; it is neither a contract key nor a flag, so an adapter that needs longer hands the work to its CI system and returns — and then kills **the whole group** — `TERM` first, then after a short grace period `KILL` (`kill -- -"$pid"`, then `kill -KILL -- -"$pid"`), so a command or descendant that traps or ignores `TERM` cannot leave the wrapper blocked in `wait` or outlive the run — and on normal completion the wrapper kills the watchdog and then **sweeps the group anyway** (`TERM`, then `KILL`, on whatever is still in it) before returning — an adapter that detaches work (`worker &`) and exits 0 would otherwise leave that work alive past the bound and past the lock's release; detached work is therefore not a thing an adapter can do from these commands, and the RFC says so rather than promising a guarantee the wrapper could not keep. So an adapter that starts a pipeline or child processes cannot outlive the bound through its descendants, a fast command does not leave a sleeping watchdog that could later signal a reused PID, and a hung adapter is killed at `N` seconds rather than outliving the run and waking the orchestrator after Step 5 released the lock. The whole wrapper is backgrounded for a hint. A hint killed that way is reported as `timed out` when its exit is collected. Step 5 is where "never waited on" ends: before it sends `run-complete` it **drains** every wrapper still outstanding from the loop — a `merged` or `run-start` launched moments before the scope went terminal — each bounded by the same `N` and all running concurrently, so the drain costs at most `N` in total; that is what makes "collected at Step 5 at the latest" true, and it is why no wrapper outlives the lock's release or wakes the orchestrator after it. Then `run-complete`, the last hint of the invocation and the one whose effect the observation pass wants to see, is waited for the same way before querying `status` (§8.2), its exit reported like any other; and `--flush` (§6.1) runs its hint in the foreground and prints the result, since nothing later would collect it. A `status` query runs in the foreground under the same wrapper, since its answer is what is wanted, so Step 5 and `--status` cost up to `N` seconds per query — one query per *distinct* merge oid, plus at most eight chain hops (§5.4), never a poll for a state change; and the pass as a whole — Step 5's or `--status`'s — has a **single deadline** on top of the per-query bound, a fixed plugin constant, **300** seconds, identical in both editions and likewise neither a contract key nor a flag, after which no further query or chain hop is started — and each query's own bound is `N` or the budget remaining before the deadline, whichever is smaller, so a query started late is killed at the deadline rather than running `N` seconds past it — and every candidate not yet answered is reported as `unavailable (observation deadline)`, so under the run lock at Step 5 a hung adapter costs the run at most `N` per query and five minutes in total, never `N` times the number of merges: that worst case is the price of the report and is bounded by construction.

Environment, versioned so an adapter can refuse what it does not understand:

It lives inside `$STATE_DIR`, so the keep-not-rotate path (a same-session re-entry, `--merge-ready`) inherits it and a rotation retires it with the rest of the run's state: one run, one id, however many invocations continue it. `flush` outside a live run sends `none`. |

An adapter keeps its candidates and windows **per branch** and applies a hint's counts only to the window of the branch the hint names — a `merged` on a branch it does not validate is ignored whole, its `REMAINING=0` included (the windows of other branches close on their own timers — `run-complete` names one branch and closes nothing on any other), and a `status` query for a revision on such a branch answers `unknown`. |

| `ISSUE_RUNNER_ISSUE`, `ISSUE_RUNNER_PR` | `merged` | the issue and PR numbers |
| `ISSUE_RUNNER_REMAINING` | `run-start`, `merged`, `run-complete` | how many issues in scope may still merge in this invocation: those `pending` or `implementing` — plus, during a `--merge-ready` pass only, the eligible `ready` issues the pass has not yet tried (dependencies `done`, PR state not yet checked): on that path the runner knows the whole batch in advance, and it is the one path where excluding `ready` would say "nothing is coming" before a backlog lands. Never counts `blocked` — the runner cannot know whether Step 4 will retry it on its own or escalate to a human; a self-resolved retry re-enters the count as `implementing`, and a `REMAINING=0` sent in between costs at most one extra validation, never correctness — nor a `ready` issue outside that pass (waiting on a human or a later `--merge-ready`), nor any terminal status. Counted **after** the merged issue's own status is written, so the last merge of a batch reads `0`, not `1`. **Under `--no-merge` it is always `0`** (the mode is known from Step 1; nothing merges in that invocation), and so is `NEAR_COMPLETE`. `run-complete` always sends `0`. |
| `ISSUE_RUNNER_NEAR_COMPLETE` | `merged` | how many `implementing` issues have a `progress` marker reading `step=9` or `step=9.2` — inside gh-issue Step 9 (full validation, ready, base freshness, the checks gate, the merge), which can still be a long `full` run or a slow CI away from merging. Advisory by construction: the marker's *content* feeds this one hint and nothing else, in keeping with the rule that it never feeds a status. |
| `ISSUE_RUNNER_REASON` | `run-complete` | `completed` (Step 5 reached with every issue terminal or paused), `paused` (host credit/usage-limit pause), `stopped` (any other exit through Step 5) |

`ISSUE_RUNNER_REMAINING` is a count, not a promise: an `implementing` issue may block, fail, hang, or take an hour. That is why the project's maximum wait, not the count, decides when to stop waiting (§7).

### 5.6 Outcomes at Step 0

`/issue-runner` Step 0 probes the file next to the validation contract and prints one of:

- `integration: not configured` — no file on the base branch. Today's behavior, unchanged; nothing else in this RFC runs. Not a notice, not a warning: most projects will never have the file (§9).
- `integration: hint` / `integration: status` / `integration: hint, status` — which commands the run will use.
- `integration: contract invalid (<reason>) — integration disabled for this run` — printed at Step 0 **and** repeated at the top of the Step 5 summary, and the run proceeds with neither hints nor observation. This deliberately differs from row 43 (a grammar-invalid *validation* contract stops the run before dispatch): validation gates every merge, so it must never silently turn off; integration gates no merge and no status, and the project's CI validates on its own timers by design (§6.3), so a broken adapter file costs a run its hints and its report — loudly — and nothing else. Stopping the run instead was considered and rejected: it would make a file that cannot affect correctness able to halt work. The runner never creates or edits the file (design-notes note 6's rule applies here too).
- `integration: unresolvable (<reason>)` — the base tip could not be fetched or read: the environment failure class. On an orchestrated run the fetch and the tree lookup are the validation-contract preflight's own (the same fetch, the same `ls-tree`), and their failure has already stopped the run before this line is reached; what stays reachable here is the one read that is per path — a blob the tree lists but `git show` cannot read, after the validation blob read fine. That case, like the two `--status` and `--flush` print (below), disables integration for this run — printed at Step 0 **and** repeated at the top of the Step 5 summary, exactly as the invalid line is — and the run proceeds: integration is disabled for want of a trusted copy, never read from the working tree instead, and never a reason to stop work the file cannot affect.

`--status` and `--flush` skip Step 0 (they never lock, rotate or initialize) and so run this discovery themselves — a fetch of the base tip and a grammar check, read-only with respect to run state — printing the same four outcomes, `disabled (contract invalid: <reason>)` / `disabled (unresolvable: <reason>)` in place of the two failure lines.

## 6. Lifecycle hints

### 6.1 What the runner knows that CI cannot, and when it says so

CI sees pushes one at a time. The runner sees run membership: how many merges are still coming, from where, and whether the run is over. Four hints carry exactly that and nothing else:

| Hint | Sent | Carries | What a project may do with it |
|---|---|---|---|
| `run-start` | once per invocation, the moment Step 3 has marked its issues `pending` and enters the loop — the first point at which every in-scope issue has a status file (a fresh run has none before that line; a re-entry still carries pre-marking statuses). A `--merge-ready` pass runs before that line and so sends its `merged` hints first; §6.2 makes that order harmless. | `REMAINING` = the `pending` + `implementing` count (§5.5) | `REMAINING>0` → open a longer quiet window for the first merge: a batch is coming. Otherwise (`--no-merge`, §5.5) nothing. |
| `merged` | each time positive merge proof is found — Step 3 item 5's classification script finds the merged PR — **and the proof is known to be this run's**: at once when item 5 writes `done`; for row 16's `blocked` open-issue case, **deferred** until the human answers Step 4's question — *this run's PR* → sent then, with the counts as of then; *a previous run's PR* → never sent, and `merge-oid` removed (§8.1). The proof alone cannot tell the two apart, and an earlier run's merge can still be `pending` on a quick re-entry (before its `W` expires), where §6.2's stale rule would not catch it: a `--no-merge` run's `REMAINING=0` would then start someone else's candidate, the very thing the `run-complete` rule below forbids. A run that ends before the answer never sends it — harmless by §6.3. And each time the `--merge-ready` pass verifies `MERGED` (its own merge, or a PR already merged by hand) | the merge oid, issue, PR, `REMAINING`, `NEAR_COMPLETE` | `REMAINING=0` → close the window now. `NEAR_COMPLETE>0` → extend the quiet window, up to the maximum wait. Otherwise nothing. |
| `run-complete` | once per invocation, from Step 5, on every exit through it — a completed run, a paused one, a stopped one — sent **first**, before the summary and the observation pass (§8.2), since its value is promptness and it depends on nothing they compute — and, alone among the run's hints, waited for (bounded, §5.5) before the observation pass queries `status` | `REMAINING=0`, `REASON`, and `REVISION` = the revision of the last `merged` this invocation sent (with `BASE` = that merge's base) — **absent** when it sent none: a `--no-merge` run, a run whose issues all blocked or failed, a re-entry that re-proved nothing | Nothing more is coming from this invocation: close the window of the candidate `REVISION` is pending in — even for a run the adapter never saw a `run-start` for — and, with or without a `REVISION`, withdraw any extension this run's `run-start` granted on the default branch's window (it falls back to `W` from its last push). Without a `REVISION`, close **nothing** beyond that: the only `pending` candidate is then someone else's — a hand merge's, another run's — and the invocation has no standing to start it early. |
| `flush` | on `/issue-runner --flush`: an invocation that, like `--status`, never locks, rotates, initializes or writes run state — but is not read-only on the project's side: it asks for a validation, which is the project's deployment to start. It runs the §5.6 discovery, sends this one hint for the current base tip **in the foreground** (the one hint with no later pass to collect its exit, so the bounded wrapper runs inline) and exits printing `flush: sent (exit 0)`, `flush: adapter exited <code>` or `flush: timed out` — an explicit request to validate now must never fail silently. When discovery yields no `hint:` command — `not configured`, `disabled (...)`, or a `status`-only file — it sends nothing and exits non-zero printing `flush: not sent (no hint command)` after the discovery line. | the base tip oid; `RUN` and `RUN_STATE` per §5.5 | Validate the tip now, whatever the window says — again, whether or not the run is known. |

Hints go from the orchestrator only. The implementer (gh-issue) sends none: it has no run-wide knowledge, and in orchestrated mode the orchestrator learns of its merge at item 5 promptly after it happens. An interactive gh-issue run and the single-issue fast path therefore send nothing — CI's own window handles a lone merge exactly as it handles a hand merge (§10). Whether gh-issue should later send a `merged` with `REMAINING=0` for that case is an open question (§14); it is not needed for correctness.

### 6.2 What hints are not

- Not commands. A hint never instructs CI to build, deploy, cancel or skip; it states a fact about the run. The verb is the project's.
- Not required. A project may declare `hint:` as `true` — or not at all — and lose nothing but batching finesse.
- Not ordered or exactly-once. A hint can be late (the orchestrator sat in a Step 4 `AskUserQuestion` for an hour; the implementer's merge landed long before item 5 read it), duplicated (a same-session re-entry re-proves a merge), or missing (the runner crashed). An adapter dedupes `run-start` and `run-complete` on `(RUN, INVOCATION, HINT)` — a second `run-start` from a new invocation of the same run is a real event (a paused run resumed, a `--merge-ready` pass) — and `merged` on `(BASE, REVISION)`: a commit is merged onto one branch once, whichever invocation re-proves it, and a `merged` whose revision already sits in a `running` or validated candidate on that branch is stale and moves no timer. Every hint is optional input to the adapter's timers, never a required one. `run-start` creates the run on the adapter's side idempotently; `run-complete` and `flush` act even on a run it never saw start — each on the candidate its own `REVISION` names, `flush` the tip, `run-complete` the run's last merge (§6.1), so neither can start a candidate that holds none of the sender's work. A `run-complete` whose revision already sits in a `running` or validated candidate is stale under the same rule as a `merged`: the run's work is being validated or has been, the `pending` candidate holds only later pushes, and the hint closes nothing. A window a hint has closed stays closed: once `REMAINING=0`, `run-complete` or `flush` has closed a candidate's window — a `pending` candidate queued behind a `running` one included — no later `run-start` or `NEAR_COMPLETE>0` extends it; a late extension may only lengthen the window of a candidate a later push created, and never past `M`. And completion is terminal for an invocation's extensions: a `run-start` or `merged` processed after the `run-complete` of the same `(RUN, INVOCATION)` — hints are backgrounded and unordered, so a slow `run-start` command, or one the adapter queued, can land after the completion Step 5 waited for — extends nothing, on any candidate: whatever `run-start` had granted, `run-complete` withdrew (§6.1), and an invocation that has said "nothing more is coming" cannot later say otherwise.
- Not evidence for the runner. Sending a hint changes no status and records only "sent (exit <code>)" for the report.

### 6.3 Fail-safe: CI never depends on runner liveness

The design rule every adapter must satisfy, stated once: **with no hint ever delivered, the adapter's behavior is correct and bounded.** Concretely, a project's quiet window `W` and maximum wait `M` (§7.1) run on the adapter's own clock from the first unvalidated push. A hint can close the window early (`REMAINING=0`, `run-complete` naming a revision pending there, `flush`) or extend it (`run-start` with `REMAINING>0`, `NEAR_COMPLETE>0`), but an extension can never move the deadline past `M` measured from that first push. So:

- The runner crashes mid-run: no `run-complete` arrives; the window closes at the latest at `M`; the merges that landed are validated. Later `--status` reads what happened. A same-session re-entry (`claude --resume`, the Recovery section) is a new invocation of the same run (`RUN` kept, `INVOCATION` new): it sends its own `run-start`, may re-send `merged` for merges it re-proves (the same `REVISION`, absorbed by the adapter's `merged` key), and sends its own `run-complete`.
- The runner pauses on a host credit stop: Step 5 runs and sends `run-complete` with `REASON=paused`. If even that fails, `M`.
- The runner is not installed: no hints, `W`/`M` alone. A `--no-merge` run sends its `run-start` and `run-complete` with `REMAINING=0` and no `merged` of its own (§5.5; a row-16 `blocked` issue's hint waits for Step 4's answer, §6.1) — so its `run-complete` carries no `REVISION` and closes nothing (§6.1): a hand merge that landed during the run keeps its own window; the human's later hand merges, or a `--merge-ready` pass's `merged` hints, are what CI sees next.
- A hint arrives in a version the adapter does not understand: ignore it (exit non-zero if it likes; the runner only records the status). A `merged` for a run it never saw start is a run it learns of now; a `run-complete` or `flush` for one closes the window of the candidate its `REVISION` is pending in regardless (§6.2) — the runner's crash-and-resume path depends on exactly that.

The plugin can verify none of this — it is the adapter's contract with itself — so the RFC states it as the one requirement a project accepts by declaring `hint:`. Nothing else in the runner's behavior changes if a project breaks it; the run finishes the same.

## 7. Coalescing

### 7.1 The window, owned by the project

Two project-chosen durations, living in the project's CI configuration and nowhere in the plugin: a **quiet window `W`** (validate once no new push has landed for `W` — minutes, not seconds; long enough for a sibling implementer at its checks gate to land) and a **maximum wait `M`** since the first unvalidated push (bounded, so a slow outlier or a dead runner never postpones validation indefinitely). The reference policy an adapter may implement — a recommendation, never enforced or observed by the runner:

1. A push to the base branch while no candidate is `pending` creates one at that oid and starts both timers. A push while one is `pending` replaces it (the old one becomes `superseded`) and restarts `W`; `M` keeps running from the first push.
2. Validation of the `pending` candidate starts when: `W` elapses with no push; or `M` elapses; or a `flush` arrives, or a `run-complete` whose `REVISION` is pending in it (§6.1 — one naming no revision, or a revision already in a `running` or validated candidate, starts nothing); or a `merged` hint with `REMAINING=0` arrives. It moves to `running`.
3. A `run-start` hint with `REMAINING>0`, or a `merged` hint with `NEAR_COMPLETE>0`, may lengthen the current `W` (say, double it) — but never past `M`; a `run-start` with `REMAINING=0` (a `--no-merge` invocation, §5.5) extends nothing, since nothing from it is coming.
4. Pushes during `running` accumulate into the next `pending` candidate under the same rules. The `running` one is not cancelled (§7.3).
5. When a `running` candidate finishes, the next `pending` one — always the newest tip, intermediates already `superseded` — is validated when its own timers say so.

The window is defined in time and in the run's counts, never in a number of PRs, because merges do not arrive in countable groups: an issue blocks, a checks gate takes twenty minutes, a human merges something in between. A count is a promise the runner cannot keep; a deadline is one the adapter keeps on its own.

### 7.2 The five scenarios

| Scenario | Pushes and hints | Candidates and states |
|---|---|---|
| **One merge** | one push; then `merged (REMAINING=0)` or `run-complete` naming that merge, or nothing | one candidate, `pending`; the hint closes the window at once, else `W` does; `running → green/failed`. Same as a hand merge. |
| **Several quick merges** | three pushes within `W` of each other; three `merged` hints with `REMAINING` 2, 1, 0 | the first two candidates go `superseded` as each newer push lands; the third is validated once — at the `REMAINING=0` hint, else at `W` after the last push. Three merges, one build. |
| **One slow outlier** | two pushes; `merged (REMAINING=1, NEAR_COMPLETE=0)`; the last issue is still implementing 40 minutes later | the `W` extension is not taken (nothing is near complete); the candidate goes `running` at `W`, at the latest at `M`. The outlier's later merge is its own candidate, validated on its own timers. The run's `run-complete` arrives whenever it does; CI never waited for it. |
| **Continuous merges** | pushes more often than `W`, indefinitely (a large run, or several actors) | `M` decides: the candidate `pending` at `M` goes `running`, whatever lands next accumulates into the next one; no candidate in `running` is cancelled; every intermediate tip is `superseded`, never validated. `M` bounds how long a tip waits before it is *eligible*, not when it starts: one validation runs at a time (§7.1 item 5), so the next starts when the running one finishes — and the queue never grows: at most one `pending` behind one `running`. |
| **Explicit flush** | `/issue-runner --flush`, or a `run-complete` naming a revision pending in the current tip | the `pending` candidate (the current tip) goes `running` immediately. If a candidate is already `running` and a newer tip is `pending`, the flush closes that pending one's window: it starts as soon as the running one finishes. If the `running` candidate *is* the current tip and nothing newer is pending, the flush is a no-op — the tip is already being validated, and queuing it again would validate the same revision twice. A flush never cancels. |

### 7.3 Supersession and cancellation

A `pending` candidate is cheap to abandon — nothing has been built — so a newer push supersedes it (constraint 6). A `running` candidate may be mid-deployment or mid-migration, and constraint 5 says a newer revision alone is no reason to stop it; the reference policy lets it finish and validates the newest tip afterwards, skipping everything in between. A project whose early phases are safely abortable may cancel in those phases; that policy is written in its adapter, and the runner neither knows nor asks — it only sees the cancelled candidate report `superseded` (§3.2's `running → superseded`) and follows it to the candidate that replaced it, exactly as for one abandoned while `pending`. The runner never sends a "cancel" hint and this RFC defines none.

### 7.4 Suggesting a short wait without waiting forever

The issue asks how the runner can suggest waiting briefly for a near-complete sibling without tying batching to `--max-parallel` and without waiting forever on a slow or blocking issue. The answer is the pair `ISSUE_RUNNER_REMAINING` / `ISSUE_RUNNER_NEAR_COMPLETE` on the `merged` hint, read against `M`:

- `NEAR_COMPLETE>0` says "someone is at the checks gate or merging" — the one moment the runner can honestly predict a merge within minutes, taken from the progress marker's step field, which exists precisely to say where an implementer is. The project may extend `W` on it.
- `REMAINING` excludes `blocked` issues, and `ready` ones outside a `--merge-ready` pass (§5.5): an issue that may be waiting on a human is not "still coming", so its wait never leaks into CI's.
- Neither count can push the deadline past `M`. A near-complete implementer that fails its `full` validation, its base refresh or its checks gate, or hangs, costs CI at most the extension it chose, never an open-ended wait.

## 8. Observation and reporting

### 8.1 Where the runner records what it needs

Step 3 item 5's classification script (`classify.sh result`) already queries the merged PR for its `headRefOid` (its one-line output grows to carry the two new fields); the same query adds `mergeCommit` and `baseRefName` and records them with the verified PR number in `$STATE_DIR/issue-N/merge-oid` (one line, `<oid> <base-branch> <pr>` — the number GitHub answered for, never `result.json`'s claim: `issue-N/pr` exists only for `ready` issues, and once Step 5 tears down a `done` issue's worktree and branch this line is the one place `--status` can read §8.2's `PR #P` from) the moment that query finds the merged PR — positive merge proof, whichever status item 5 then writes: `done`, or the `blocked` of row 16 that Step 4 later resolves to `done` (the `--merge-ready` pass records it likewise when it verifies `MERGED`). The *record's* trigger is the proof, not the status — the push has happened either way, and `--status` must be able to ask about it — while the `merged` *hint* for a row-16 `blocked` issue waits for Step 4's answer (§6.1); with one cleanup: when the human answers Step 4's row-16 question with *a previous run's PR* (the stale-branch sub-case), Step 4 removes `issue-N/merge-oid` before whatever it does next — the retry with guidance, or the at-cap escalation's `failed` — so an issue that then fails, blocks, or waits out a pause before a new merge does not let Step 5 or `--status` report that earlier run's candidate as one of this run's merges. Until that answer the record is **unconfirmed**: a concurrent `--status`, or a Step 5 reached before the answer (a run that ends first, §6.1), still queries it and prints it marked with the issue's `blocked` status — `--status` beside its row-16 `error`, Step 5 in the Integration section's per-issue statuses (§8.2) — the marker that whose PR it is has not been decided; an unconfirmed record never by itself puts its candidate on Step 5's failed-at-the-top line (§8.2); the removal covers the answered case only. This is Step 4's own removal, not a side effect of dispatch: a retry into a known worktree clears only `progress`, `result.json` and `agent` and keeps `branch`, `worktree` and `error` (Step 3a). That oid is the `merged` hint's `REVISION` and the `status` query's key, and the branch beside it is both calls' `ISSUE_RUNNER_BASE` (§5.5) — recorded because row 16 admits a merge to a non-default base, and a hint that named the default branch for it would point the adapter at a candidate that does not exist there. Both are written from GitHub's answer for the PR the proof matched, never from `result.json`, so the merge-proof rule (row 14: the file is a claim, never proof) is untouched.

### 8.2 When the runner looks

- **`--status`**: for every issue with a `merge-oid`, run `status` (when declared — `--status` runs the §5.6 discovery itself), follow `superseded` chains, and print `#N  <status>  (PR #P, merge abc1234)  integration: <state> candidate def5678 <detail>` — `P` and the oid from `merge-oid` (§8.1), `<status>` read from `issue-N/status`, never assumed: a `merge-oid` is recorded on merge proof (§8.1), so a row-16 `blocked` issue carries one before its human confirmation and must not print as `done`. It writes nothing: `--status` never locks, and a lockless write into a possibly live run's `$STATE_DIR` would race Step 5's own. `unavailable` prints as such, followed by the last observation from `issue-N/integration` when there is one, marked with its timestamp as stale — the one reader that file has besides a post-mortem.
- **Step 5**: the same, once, under the run lock, after `run-complete` has been sent **and its wrapper has returned** (§5.5 — a background launch alone orders nothing against the foreground `status` queries that follow; the wait is bounded by the hint's own `N`, and it is what lets the observation read `running` rather than `pending` — for an invocation that merged something: one that sent no `merged` sends a `run-complete` that closes nothing, §6.1, and has no merge of its own to observe — earlier invocations' `merge-oid` files are still queried, their windows closed, or not, by those invocations' own hints) and after the summary table, as an "Integration" section grouped by candidate — `(branch, oid)`, §3.2 — in `dag.json` order — one line per candidate listing the issues it contains with their `status` — an unconfirmed row-16 `blocked` one marked as such (§8.1) — so three coalesced merges read as one `running` build, not three — and this is the one place `issue-N/integration` (§3.2) is written. It ends with `re-check: /issue-runner --status`. The section is posted with the summary to the tracking issue when the summary is (row 20), and `<detail>` and the oids pass through the same cell sanitization Step 5 applies to `title`, `error` and `last progress` — newlines collapsed, backticks replaced, `|` escaped, code-spanned — with `<detail>` cut to the first 200 bytes of its first line before that: it is a project command's stdout, and outbound to GitHub it is data exactly as inbound issue text is (an `@`-mention or `#N` in it must not fire a notification or a cross-link). A `failed` candidate containing this run's merges is also stated at the **top** of the closing message, ahead of the summary, the way a host pause is: it is the one integration outcome a human must act on — except a candidate whose only issues in this run are unconfirmed row-16 `blocked` ones (§8.1): it is listed in the section under that status but does not by itself produce the top line, since whether it contains this run's merge at all is the question the human has not yet answered — the closing message and the tracking-issue comment are assembled once, after the observation pass, so that line and the section come from the same query.
- **Never** in a loop. Step 5 does not wait for `pending` or `running` to resolve: a run's end is when its issues are terminal, not when a deployment finishes, and a bounded wait at Step 5 (`--await-integration <minutes>`) is listed as a possible follow-up in §14, not proposed here.

### 8.3 What the runner never does with what it sees

- **Never changes a status.** A `failed` candidate does not make any issue `failed`, `blocked`, or anything else; `done` is merge proof and stays so (row 14's family). The `integration` file is informational, like `progress`.
- **Never gates dispatch** in this RFC. A dependent of a `done` issue dispatches when the scheduler says so, on the base branch as it is. The argument for gating — do not build on a revision E2E just rejected — is real, and the plugin already holds the code-level half of it: the dependent's implementer merges the base in and runs `preflight` on the sum (Step 9's base freshness, run early on a failing preflight), so a base broken at the unit level blocks at the dependent's own preflight. The system-level half (a green build that fails E2E) is what integration state adds, and pausing dispatch on it is a policy a project may want. It is deferred (§14) rather than built here because it is the first place integration state would *decide* something, and the right shape — an opt-in flag, the same run-wide pause the credit stop uses — deserves evidence from reports first.
- **Never reverts, never retries, never re-validates.** The recovery for a red candidate is the project's and a human's: a fix-forward PR (which the runner can implement, as any other issue), a revert, a re-run of the pipeline. `--flush` is the only thing the runner offers, and it only asks.
- **Never authorizes a merge.** No `green` anywhere shortens a review loop, skips a checks gate, or excuses a failing preflight. The validation contract's "both must hold" (preflight and CI) becomes "all three are independent": preflight, CI checks on the PR, integration of the revision.

## 9. Why `--max-parallel` is not a batch size

`--max-parallel` bounds how many implementers run at once: memory, host budget, Codex spend, review-slot pressure. It says nothing about when merges land:

- In-flight count varies over the run with the DAG's shape — one issue at a bottleneck, `N` on a wide layer — so "wait for `N` merges" is either instant or never.
- Implementers finish at different times: one converges in ten minutes, its sibling bounces twice at the Codex gate. A batch of `N` waits on the slowest, which is exactly the outlier problem §7.2 avoids.
- Some issues never merge in this invocation (`blocked`, `ready`, `failed`, `skipped`), so an `N`-sized batch may not fill.
- `--sequential` (`N=1`) would validate every merge; `--no-merge` runs merge nothing at all; `--merge-ready` merges a whole backlog in one pass with `N` irrelevant. Hand merges (§10) are outside `N` entirely.

A batch is therefore whatever lands within the project's `W`/`M` window, informed by `REMAINING` and `NEAR_COMPLETE`. Changing `--max-parallel` changes how fast merges arrive, and the window absorbs that; it never changes what a batch is.

## 10. Projects with no CI, human merges, and changes made outside the runner

**No CI/CD at all** — the common case for this plugin's users today: no `.issue-runner/integration`, so Step 0 prints `integration: not configured`, no hints are sent, nothing is observed, Step 5 has no "Integration" section, and the run behaves exactly as it does now. A project with CI but no adapter is the same case: CI runs on its own triggers, unaware of runs, as it does today. Nothing in this RFC is a requirement on a project; §5.6's `not configured` is a statement, not a warning.

**Human merges and work outside the runner** — a hand merge, a hotfix, a `--no-merge` PR merged by a human (a `--merge-ready` pass, by contrast, continues the run and does send `merged`, §6.1): all are pushes to the base branch, and the adapter's trigger is the push, not the runner. They become candidates under `W`/`M` like any other, with no hints, and are coalesced with a run's merges when they land inside its window — a candidate is a tip, and a tip contains whatever was merged. The runner's report covers only candidates that contain *its* merges (it has no other key to ask with), so a hand merge shows up there exactly when it shares a candidate with the run's work. That is the right scope: the runner reports on what it did; the project's own dashboards report on everything.

## 11. Reconciliation with what exists

### 11.1 Base freshness (gh-issue Step 9, issue #15) and `--merge-ready` (row 37)

Base freshness is a **pre-merge, per-PR, code-level** guarantee: whenever `origin/<base>` advanced since the branch point, the implementer merges it in and re-runs `preflight` and `full` before the checks gate, so each PR is validated against the base it actually lands on — the two-trains window closed without a queue. The `--merge-ready` pass goes one step further at its own later merge point: it syncs the worktree to the PR's current head, merges the base in if it advanced, re-runs the contract's validation on that head *whether or not* the base advanced (row 37), and pins the merge to the validated oid (`--match-head-commit`).

Integration validation is **post-merge, per-revision, system-level**. It composes with freshness rather than overlapping it: freshness makes each merge individually sound; integration validates their sum in an environment no worktree has. Nothing in this RFC moves, weakens or duplicates the freshness recipe, and the `--merge-ready` pass changes in exactly one way: after `MERGED` is verified and `done` written, it records `merge-oid` (the oid, the PR's `baseRefName` and its number, §8.1) and sends `merged`. The pin is on the validated PR *head*; the hint names the `mergeCommit`, a different commit under `--squash` — and the pin is what guarantees that commit contains exactly the validated head and nothing pushed after the refresh, which is why it matters here too.

### 11.2 Invalid contracts (row 43) and the override rule (row 44)

Row 43's invariant — a broken validation contract never degrades silently into "no validation" — stands untouched, because this RFC never touches `.issue-runner/validation`. The integration file has its own, weaker rule for a *broken* file (§5.6: disabled loudly), and §5.2 explains why the two must not share a file. Row 44's rule — text in an issue, PR, comment or `guidance.md` never changes which command runs, and a PR that edits the file is merged only by a human — applies to `.issue-runner/integration` in full: the same discovery recipe and the same Step 9 `changed`-mode gate, extended to the second path, with the same mixed-version limit (§5.3).

### 11.3 The parked merge queue (design-notes note 2)

Note 2 parks the queue's serialization ("one merge token, one PR through it at a time") until parallelism outgrows conflict-edge serialization, and records the cheap fix — unconditional base merge and re-test — as implemented. This RFC neither builds the queue nor contradicts the parking:

- It does not serialize merges. Coalescing several merges into one candidate is the opposite instinct: let merges land as they converge, validate the tip once.
- It does not gate merges on integration state (§8.3). Gating a merge on the previous revision being `green` would be a merge queue *plus* a deployment in the merge path — the "second CI engine" constraint 3 forbids.
- If the queue is ever built, the contract is unchanged: `merged` hints simply arrive one at a time through the token, and `NEAR_COMPLETE` gains a precise meaning (the implementer holding the token).
- It supplies a signal note 2 currently lacks. "Revisit above ~6 parallel slices" needs evidence that semantic conflicts are landing; a `failed` candidate whose issues each passed their own freshness check is the first place such evidence would show up, reported per run — a candidate for the human to read, not proof: a flaky E2E suite or an infrastructure failure produces the same state, and the runner cannot tell them apart.

Note 6 (who writes the first validation contract) applies to this file verbatim: the runner never writes a guessed `.issue-runner/integration`; a human, or a later confirmed proposal path, does.

## 12. Promotion, later

A candidate is a base-branch oid; a `green` one is exactly the revision a production promotion should ship. The design keeps that door open by keying everything on the oid and by never asking the project to *build* anything — hints ask for validation of a revision, and the artifact that validation produced is the adapter's to keep, addressable by the same oid. A future `promote: <command>` key with `ISSUE_RUNNER_REVISION` set to a `green` candidate would reuse that artifact rather than rebuild it (constraint 8). Nothing here defines it.

## 13. Non-goals

- No CI/CD technology is named in the contract, the runner, or the docs beyond illustration; no Link21-specific behavior, no reference adapter shipped with the plugin — a script under `skills/` would ship everywhere (the portable-context packaging carries the whole `skills/` tree plus `plugin.json`, `scheduler.sh` included), which is exactly the technology coupling this non-goal refuses; the contract is a file convention in the target repository, like `.issue-runner/validation`.
- No integration state in `result.json`: the implementer never observes integration, and the key set is lint-pinned across four files; the `validation:` line's precedent (prose, not a key) applies.
- No new issue status, no scheduler change, no `docs/scenarios.md` Expected-behavior change — this RFC is documentation; the implementation slices in §14 would each add their rows.
- No waiting at Step 5, no cancellation, no environment reservation, no promotion, no adapter-side state store owned by the plugin.

## 15. Implementation notes: slice 1 (issue #60)

Slice 1 ships as one bundled script, `skills/issue-runner/scripts/integration.sh`, with a byte-identical Codex copy. Its header holds the grammar, the environment table and the bound. `scripts/test-integration-contract.sh` fixtures them, and `docs/scenarios.md` rows 67–72 are the contract. Where the build differs from the sections above, this section is authoritative:

1. **Hints detach themselves.** §5.5 starts each hint with the host's `run_in_background` and collects its exit in the Step 3 loop. Instead, `integration.sh hint` builds the environment, forks its bounded wrapper with `nohup … &` and returns at once. Every exit is collected by Step 5's drain (`integration.sh run-complete`), so "collected at Step 5 at the latest" holds and the Step 3 loop does not change. The Codex host ends a shell call's descendants when the call returns, so the Codex wrapper sets `INTEGRATION_HINT_FOREGROUND=1`. Each hint then runs in the foreground under the same 60-second bound. A wrapper called in the foreground (`run-complete`, `flush`, the Codex hints) traps TERM, INT and HUP and takes the command's process group down with it. A detached wrapper starts under `nohup`, so it traps only TERM. A SIGKILL of the wrapper cannot be trapped, so a host that kills that way leaves the adapter running past the bound.
2. **`merge-oid` is written by the classification script itself.** §8.1 grows `classify.sh result`'s output line instead. In the build, the merged-PR query adds `mergeCommit` and `baseRefName`, and the script writes `issue-N/merge-oid` (`<oid> <base> <P>`) on merge proof, both for `done` and for row 16's `blocked`. Its output line is unchanged. The record is best-effort: an abbreviated or missing oid records nothing. In the `--merge-ready` pass, `integration.sh hint … merged <N> --pr <P>` records it from `gh pr view` after `done` is written.
3. **`run-id` and `invocation`.** `run-state.sh init` writes `run-id` as `<repo-key>@<ISO-8601 UTC>-<pid>-<random>` whenever the state dir has none. That covers the fresh path, and it covers the keep path's one-time mint for state left by an older plugin. It never overwrites a non-empty file. Every `init` also writes `invocation`, which is `ISSUE_RUNNER_INVOCATION`, with the same suffix. Second-resolution time alone would give two inits in one second the same ids, so their hint results and last `merged` revision would be conflated.
4. **Discovery runs twice in an orchestrated invocation.** Step 0 prints the line. After `init`, the State section re-runs discovery with `$STATE_DIR` to record the contract for that invocation's hints, and its line supersedes Step 0's. Step 0's probe does its own fetch and `ls-tree` rather than sharing the validation preflight's (§5.6), so a fetch failure there prints `integration: unresolvable (…)`. As §5.6 requires, that disables integration and never stops the run.
5. **`REMAINING` in the `--merge-ready` pass** counts the issues the orchestrator passes as `--untried` that are still `ready` with every `dag.txt` dependency `done`. The pass knows which issues it has not tried yet, and the script checks the rest.
6. **Both contracts edited in one PR.** The validation script's `changed` mode prints a line for each file. gh-issue Step 9's blocker names the validation contract, and the `--merge-ready` refresh's *stuck* reason is the validation one. The `integration contract …` wording is used only when that file alone changed.
7. **`--flush` liveness.** The call takes `<lock-ttl-minutes>` and treats the run as live under the run lock's own rule: a live PID, or a heartbeat younger than the TTL.
8. **Step 5 output.** `run-complete` prints the disabled line, if any, and one line per hint of the invocation. Step 5 prints them at the top of its summary. Posting them to the tracking issue belongs with slice 2's "Integration" section.
9. **The reason `run-complete` sends.** It is `paused` while `$RUN_ROOT/paused` exists, `stopped` after a Step 4 risk-blocker abort, and `completed` otherwise.
10. **A test-only knob.** `INTEGRATION_HINT_BOUND` overrides the 60-second bound for the fixtures, like `MERGE_READY_POLL_SLEEP`. It is not a flag or a contract key.
11. **The drain's actual guarantees.** §5.5 says the drain costs at most `N` and that no wrapper outlives the lock's release. The build is weaker in three ways.
    - The drain waits at most `N` plus 10 s. A marker older than `N` plus 15 s is treated as dead.
    - An earlier invocation's leftover markers are dropped without a report line.
    - A wrapper still running at the deadline is reported as `not collected (still running at Step 5)` and its marker is removed. If it has not started, it never starts. If it is already running, it finishes under its own bound, so it can outlive the lock's release by at most that bound. Marker age is wall-clock time, so a host suspend during a hint can make the drain give up on it early. It still ends under its own bound.
12. **One more `--flush` outcome.** When the wrapper cannot create its private watchdog directory, `--flush` prints `flush: not sent (cannot create the watchdog directory)` and exits 1. A hint that fails this way reports the same text at Step 5.
