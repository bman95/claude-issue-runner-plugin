# Golden scheduler scenarios

These fixtures are the behavioral contract of the orchestrator's scheduling loop (`skills/issue-runner/SKILL.md`, Step 3 and its satellites). Each row was verified by dry-reading the spec against the scenario; a spec edit that changes any **Expected behavior** cell is a **breaking change** and requires a version bump plus a CHANGELOG entry. After any edit to Step 3, Step 3a, or Step 5, re-dry-read every row below. Anchors cite step/item numbers, never line numbers — the file is edited too often for lines to hold.

Notation: `A -> B` means B depends on A (edge B→A in `dag.json`). Statuses are the spec's own vocabulary: `pending` / `implementing` / `blocked` / `done` / `failed` / `skipped` / `closed-externally` / `ready`.

Rows 1, 2, 3, 4, 29, 32 and 34 are the pure state machine — cascade skip, the ready set, and the blocked-chain-vs-run-paused-vs-cycle distinction (Step 3 items 1, 2 and 6) — and have an **executable** form: `skills/issue-runner/scripts/scheduler.sh` implements the transitions (its own comments are the one statement of the rules) and `skills/issue-runner/scripts/test-scheduler.sh` encodes each of those rows as a fixture, run from `scripts/lint.sh` and so from CI. Rows 5, 6, 11, 14, 15, 16, 17, 18, 21, 23, 24, 25 and 35 have an executable form for their classification only. That is Step 3 item 5's merge proof, and Step 5's label for an unfinished PR or orphan branch. `skills/issue-runner/scripts/classify.sh` implements both, and `skills/issue-runner/scripts/test-classify.sh` fixtures each of those rows against a stubbed `gh` and real temporary git repositories, also from `scripts/lint.sh`. The rest of those rows (a stop, a resume, a revert to draft) is still verified by dry-reading. Rows 7, 8, 22 and 23 have an executable form for Step 3a's resume probes and their classification (`skills/issue-runner/scripts/resume-check.sh`, fixtured by `test-resume-check.sh`), and row 37 for the mechanics of the `--merge-ready` pass — the PR state, the refresh, the checks re-check and the head-pinned merge (`skills/issue-runner/scripts/merge-ready.sh`, fixtured by `test-merge-ready.sh`), both run from `scripts/lint.sh`; what the orchestrator then decides (resume, ask, the status it writes, the summary line) is still verified by dry-reading. The remaining rows exercise Step 3 items 3–5 (dispatch, hang detection, result.json processing), Step 3a, Step 4, Step 5, or Step 1/2/State, gh-issue's validation contract (rows 39–44), or the planner's reconciliation with existing work (`skills/issue-plan/SKILL.md` Step 2, rows 45–49), or gh-issue's Codex gate cap (row 50), its user-authorized prose review profile (rows 51–59), and its reviewer and gate liveness (rows 60–62) — judgement or live-GitHub work outside a pure status-files-and-`dag.txt` state machine — and stay verified by dry-reading, as this whole table always has been.
