# Golden scheduler scenarios

These fixtures are the behavioral contract of the orchestrator's scheduling loop (`skills/issue-runner/SKILL.md`, Step 3 and its satellites). Each row was verified by dry-reading the spec against the scenario; a spec edit that changes any **Expected behavior** cell is a **breaking change** and requires a version bump plus a CHANGELOG entry. After any edit to Step 3, Step 3a, or Step 5, re-dry-read every row below. Anchors cite step/item numbers, never line numbers — the file is edited too often for lines to hold.

Notation: `A -> B` means B depends on A (edge B→A in `dag.json`). Statuses are the spec's own vocabulary: `pending` / `implementing` / `blocked` / `done` / `failed` / `skipped` / `closed-externally`.

| # | Scenario (DAG + statuses) | Expected behavior | Spec anchor |
|---|---------------------------|-------------------|-------------|
| 1 | `A -> B`; A is `blocked`, nothing else in flight | B stays `pending` (paused). It is a blocked-chain waiter, **never** skipped as a cycle; resolution goes through Step 4 on A. | Step 3 item 1 (last sentence) + item 6, blocked-chain case |
| 2 | `A -> B`; A ends `closed-externally` | B → `skipped` with error `"dependency closed externally without merge proof: #A"`. A is terminal but unverified; B must not build on it and must not be mislabeled a cycle. | Step 3 item 1 (closed-externally cascade) |
| 3 | `A -> B`; A ends `failed` | B → `skipped` with error `"dependency failed: #A"`; cascade repeats until stable. | Step 3 item 1 (cascade skip) |
| 4 | True 2-cycle: A depends on B, B depends on A; no `blocked` ancestor anywhere | Both → `skipped` with `error="cycle: depends on #X"` citing a real offending dep; loop exits. | Step 3 item 6, true-cycle case |
| 5 | Issue reports `CLOSED` and a **merged PR exists on the implementer's branch** | Issue → `done`. This is the only status that authorizes Step 5's `git branch -D` (positive merge proof). | Step 3 item 5, first bullet; Step 5 done-issue teardown |
| 6 | Issue reports `CLOSED` but **no merged PR** on that branch | Issue → `closed-externally`: error note saved, **worktree and branch kept**, flagged in the Step 5 summary as a non-zero outcome. Never `-D` its branch. | Step 3 item 5, second bullet; Step 5 summary rules |
| 7 | Re-run; an open PR exists whose head branch matches `/issue-N-` | Resume: dispatch checks out the existing branch and pushes to the existing PR — no duplicate PR is ever opened. | Step 3a resume check, one-match case |
| 8 | Re-run; the resume branch is still checked out in a leftover worktree | Dispatch **without** `isolation: worktree`; the agent `cd`s into the existing worktree and reuses it (git refuses one branch in two worktrees). | Step 3a resume check, one-match worktree sub-case |
| 9 | Scope size == 1 | Fast path: no state init, no DAG, no Step 5. The gh-issue procedure runs inline as an interactive run; gh-issue owns worktree lifecycle. | Step 1 single-issue fast path; Hard rules (fast-path rule) |
| 10 | `git status --porcelain=v1 -uall` reports anything at start | Show every line and ask: stash / commit / discard / proceed-as-is. Never start orchestration on a dirty tree silently. | Step 1 dirty-tree audit |
| 11 | Issue reports `CLOSED` but `WT_BRANCH` is empty/unreadable (worktree gone) | `closed-externally`, **never** `done` — a missing worktree is no merge proof. (Open + gone worktree → `failed`.) | Step 3 item 5, empty-`WT_BRANCH` guard |
| 12 | `implementing` issue whose `progress` file is missing, empty, stale, or reads `step=9.2` | No status change from the file alone — statuses come only from the agent's result and item 5's merge proof. `--status` prints the line as data (or `no progress recorded`). If the issue later ends `failed`, Step 5 cites the line as where it stopped, never as evidence of merge or convergence. | State section (`progress`); Step 3a (cleared at dispatch); Step 3 item 4; Step 5 summary |
| 13 | `blocked` issue whose `retries` already equals `--max-retries` (default 2) returns another blocker — even one the parent could answer itself | **Never auto-retried.** Escalate to the user with the full retry history (every `## Retry K` section of `guidance.md` plus the current `error`) and a recommendation. A retry the user authorizes still increments `retries`, so the Step 5 summary shows the true spend. Under the cap the same blocker would have been self-resolved via `guidance.md` + retry. | Step 4 (cap rule; retry escalation increments `retries`); State section (`retries`); Step 5 summary |
| 14 | Re-run; the open PR matching `/issue-N-` is a **draft** whose body carries `## Plan` (the implementer died before implementing) | Resume, same as row 7: the implementer confirms the branch holds only the checkpoint commit, takes the plan from the PR body (verified against the issue), continues from gh-issue Step 5 and rewrites the body at Step 7; no second checkpoint, no duplicate PR. A branch with further commits is a partially executed plan — continue it, never re-execute it. If the run ends with the PR still a draft, the Step 5 summary lists it as `draft (checkpoint)` while the body still carries `## Plan`, or `draft (implemented, not ready)` once Step 7 rewrote it — never ready-to-merge. | Step 3a resume check, `draft=true` match; Step 5 summary; gh-issue Steps 3–4 |
| 15 | Re-run; no open PR for N, but `origin/<type>/issue-N-<slug>` exists (the run died between the checkpoint push and `gh pr create`) | Probe 3 finds the branch and classifies it by PR history: no PR → true orphan, resume on it with no PR yet (gh-issue Step 4 opens the draft checkpoint on the existing branch), never a fresh dispatch (its checkpoint guard would blocker every time); merged PR with the tip still at its `headRefOid` → stale debris, delete and dispatch fresh; merged but moved on, or closed PR → ask the user. Step 5 lists an orphan as `branch only (no PR)`. | Step 3a probe 3, branch-only case; Step 5 summary |
| 16 | An implementer converges, readies its PR, then blocks below the ready line (base-freshness conflict, failing checks) | The PR is reverted to draft (`gh pr ready --undo`, attempted unless a re-queried `isDraft` is positively `true`) before the blocker returns, so every orchestrated PR that *returns* unfinished is a draft — or, if the revert failed, its blocker says the PR is still mergeable; Step 5 labels it `draft (implemented, not ready)` (or names it as human-mergeable). | gh-issue Step 9 blocker rule; Step 5 summary |
| 17 | An implementer readies its PR and then crashes before `gh pr merge` (no blocker ran) | The PR is left non-draft. Step 5 labels it from body and branch like a draft and names it as the one unfinished PR a human could merge by hand. | Step 5 summary, non-draft cases |

Two rows (1 vs 4) together pin the 0.7.0 cycle-check fix: a cycle is declared only when **no** remaining `pending` issue has a `blocked` ancestor. Rows 5, 6 and 11 together pin the merge-proof invariant: `CLOSED` alone never authorizes branch deletion. Row 13 pins the retry cap: past `--max-retries` the parent never re-dispatches on its own authority.
