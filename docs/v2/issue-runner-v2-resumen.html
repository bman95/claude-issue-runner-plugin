Issue Runner v2

De issue de GitHub a PR fusionado con agentes Claude Code y Codex. Un programa determinista lleva el control, los agentes solo emiten juicios acotados, y no se fusiona nada sin evidencia ligada al commit exacto.

La idea central

En v1, Claude ejecuta como orquestador unas 68.000 palabras de instrucciones. Sus fallos en producción fueron, sobre todo, fallos de interpretación de esa prosa: pasos omitidos, resúmenes parafraseados, aprobaciones inventadas. v2 invierte el control.

Coordinator determinista

CLI en Python con SQLite. Una máquina de estados con transiciones transaccionales. Ningún LLM decide el flujo.

Agentes como procesos acotados

claude -p y codex exec. Cada uno recibe un contrato de entrada y devuelve JSON validado contra un esquema. Sin hooks.

Los agentes proponen, el coordinator decide

Ningún agente escribe en GitHub ni fusiona. El coordinator ejecuta acciones de un catálogo cerrado, con gh.

Arquitectura

Alternativas descartadas como núcleo:

  • Temporal: servidor adicional.
  • LangGraph: sin temporizadores y sin cancelación de nodos en ejecución.
  • GitHub Agentic Workflows: Actions con tokens de suscripción.
  • Agent SDK: pide API key para productos.
  • Code Review gestionada: no bloquea y cuesta aparte.

Ningún framework resuelve la idempotencia en GitHub ni la supervisión de procesos: eso es trabajo nuestro en cualquier caso.

Flujo de una issue

  1. Triage determinista. Lint AI-Ready: qué construir, criterios con Verify: (http, browser, cli, inspection), Blocked by, ficheros probables, fuera de alcance, riesgo. Un bug necesita reproducción o una razón escrita de por qué no la tiene.
  2. Preparación con Opus si la issue no es AI-Ready. Las preguntas de producto van a una persona. Una persona con permiso de escritura aprueba con ir:ai-ready. Se congela la spec, y si cambia, el ítem se pausa.
  3. Reclamo e implementación con Sonnet. La issue se asigna al usuario para que otro runner no la tome. El implementador trabaja en un worktree, sin push ni gh. En bugs escribe primero un test que debe fallar en la base.
  4. Validación determinista. preflight del contrato de la base y ejecución de las líneas Verify: por el Validator. Después se hace push y se abre un draft PR.
  5. Revisiones en paralelo sobre el mismo SHA. Code Review, Security Review y Codex Reviewer, más CI. Son prompts propios con el diff explícito, no los comandos nativos.
  6. Coordinación determinista. Ejecuta los tests de reproducción de los revisores, agrupa y clasifica los hallazgos. Llama a Opus como juez solo ante ambigüedad, disputa o desacuerdo de dirección.
  7. Correcciones con Sonnet, hasta 4 rondas. Si el bucle se estanca, Opus elige una salida: Codex Fixer, varios implementadores (si están activados), volver a especificar la issue, o una persona.
  8. Verificación previa al merge. Todas las puertas se comprueban sobre el mismo snapshot: spec, base, cabeza, política, validación y entorno.
  9. Merge serializado. Se refresca la base con merge (nunca rebase), se revalida, y se fusiona con merge-async y el sha fijado. Hace falta una aprobación con ir approve en riesgo medio o alto, o siempre en repos con merge_mode: request_only.
Cada bucle consume un contador limitado: rondas, adjudicaciones, Codex Fixer, refrescos de base, reintentos. Las esperas (cuota, base en rojo, humano) tienen plazo y avisan. Solo una persona reinicia los contadores, así que todo ítem termina o queda esperando a alguien de forma visible.

Revisión basada en evidencia

La investigación cambió el diseño en un punto clave. Pedir a un revisor que explique y arregle dispara los rechazos de código correcto (Jin y Chen, 2026). Y un revisor que reescribe puede romper código correcto (Xiang et al., 2026). Por eso:

Regla

Evidencia ejecutable

Los revisores pueden aportar un test de reproducción, y lo ejecuta el coordinator. Si el test pasa sobre el candidato, la objeción queda refutada. Una objeción solo de razonamiento nunca bloquea por sí sola: el juez Opus tiene que aportar un contraejemplo.

Regla

Sin hallazgos es válido

No se pide proponer arreglos. Un revisor puede abstenerse. No poder verificar algo no es un defecto. Codex interviene solo ante un defecto demostrable y conserva la estructura del autor.

Regla

Cerrar exige a otro

Que el implementador diga "arreglado" no cierra nada. Para cerrar hace falta evidencia de alguien distinto del autor del fix: un test que ahora pasa, el revisor confirmándolo, o Opus si el fix es de Codex.

Seguridad

Fail-closed con riesgo alto

Un hallazgo de seguridad bloquea siempre en riesgo alto, o con evidencia concreta. En los demás casos lo verifica el juez con un escenario de explotación. Un hallazgo preexistente se avisa en privado.

Protección

Plano de control

Si el candidato cambia .claude/, .mcp.json, AGENTS.md, CI, el contrato de validación o los scripts que ese contrato ejecuta, va a revisión humana antes de que corra ningún agente. Los tests debilitados se detectan de forma automática.

Codex Fixer

Puerta contrafactual

El parche de Codex se prueba antes y después, y se cuentan arreglos y regresiones por separado. El commit lo hace el coordinator. Después lo revisa un Opus Reviewer en una ejecución nueva. La aprobación del propio Codex no cuenta para su fix.

  • Entorno limpio (env -i). Se eliminan ANTHROPIC_API_KEY, CODEX_API_KEY y GH_TOKEN, para no facturar API sin querer.
  • Modo de permisos siempre explícito. Se pasa siempre --permission-prompts none, y nunca --dangerously-skip-permissions.
  • Éxito = código de salida 0, success sin error, más de 0 tokens de salida y JSON válido. En pruebas reales, claude -p devolvió 0 y success con la autenticación fallida.
  • Cada intento lleva un token de fencing. Un resultado tardío de un intento cancelado nunca hace avanzar el estado.

Puertas antes del merge

Ejecución

  • CI en verde sobre el SHA exacto.
  • preflight y full en verde con la base actual.
  • Todas las líneas Verify: pasan.
  • status: green del contrato de integración, si el repo lo declara.

Revisión

  • Cada commit está cubierto por todos los revisores requeridos.
  • Ningún hallazgo bloqueante abierto.
  • Aprobación del Opus Reviewer si hubo Codex Fixer.

Integridad

  • El snapshot no ha cambiado: spec, política, validación y entorno.
  • El plano de control está intacto o hay una autorización humana.
  • Aprobación con ir approve según el riesgo o el merge_mode.

El resultado se publica como commit status issue-runner/gate, exigido por el ruleset. Protege frente a merges manuales por error. El runner nunca fusiona si sus propias puertas no están en verde. Ante un resultado incierto, repetir merge-async con el mismo sha no fusiona dos veces.

Persistencia, memoria y recuperación

Estado

SQLite con transacciones y eventos solo de anexado, y un outbox para push, comentarios y merge. GitHub es el espejo público: etiquetas ir:*, tarjeta del PR y draft PR como checkpoint.

Memoria

El dossier de cada ítem genera un brief determinista. La memoria del repo vive en CLAUDE.md y AGENTS.md, con cambios propuestos por PR. El Registry no se inyecta en los prompts. Sin RAG.

Recuperación

Al arrancar, el runner reconcilia con GitHub antes de actuar. Una lectura fallida nunca se toma por "no existe". Hay tests que matan el proceso en cada frontera de estado. Se conservan las 26 invariantes de v1 y unos 640 asserts portables.

Evaluation & Evidence Registry

  • Desde el primer día: por cada intento, uso y resultado.
  • Por cada hallazgo: qué revisor lo encontró y cómo acabó (confirmado, refutado, cerrado con evidencia).
  • Por cada revisor: su precisión propia.
  • En las reescrituras: arreglos y regresiones por separado.
  • Después del merge: supervivencia del código, reverts y bugs posteriores.

Cada cambio de política cita una hipótesis con evidencia. Dos ejemplos: H-18, si Codex aporta hallazgos que nadie más ve; H-26, si 4 rondas son el límite adecuado. Cada semana, una persona revisa una muestra de transcripciones.

Más adelante: modo sombra (v2.1) y repetición sobre issues históricas con tests ocultos (v2.2). Con cada modelo nuevo, cada componente se quita de uno en uno para comprobar si sigue aportando.

Qué se incorporó de fuera

Investigación

Anthropic (separar workflow y agente, evaluador independiente), Agentless (tests de reproducción), OpenHands (supervivencia del código), GitHub (merge-async con sha), Temporal y LangGraph (descartados). iCoder no se pudo leer (403) y no se usa.

Diseño Sol 6.1

Snapshot de seis campos, tokens de fencing, ciclo de vida de los hallazgos, resultado firmado por el runtime, protección de los scripts de validación, cuota desconocida no es ilimitada, retención.

vela91/dev-harness

Hallazgos de pruebas reales: éxito con tokens mayores que 0, los comandos nativos no sirven como revisores, stdin cerrado en Codex. Ideas: Verify: por criterio, ir doctor, merge_mode: request_only, estado del pipeline.

Primera versión y plan

v2.0 trabaja un repo y una issue a la vez, con el flujo completo menos dos piezas: el Codex Fixer y los varios implementadores. Un estancamiento sale solo a "volver a especificar" o a una persona. El piloto se hace sin merge automático.
